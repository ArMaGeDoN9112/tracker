# API личного каталога

Все маршруты приватные и возвращают `Cache-Control: no-store`; запись требует
существующие cookie сессии, `Origin` и `X-CSRF-Token`. Названия, значения и UUID
операций передаются только в JSON-теле. Лимит тела — 65536 байт.

- `GET /api/products` — все карточки, включая архивные, с полным упорядоченным
  набором порций; изначально `[]`. Поиск по подстроке без учёта регистра (включая
  кириллицу) выполняется клиентом; поискового параметра API нет.
- `GET /api/products/{id}` — текущая карточка, в том числе архивная; отсутствующая — 404.
- `POST /api/products` — создание. Сервер назначает UUID карточки и редакцию 1.
- `PUT /api/products/{id}` — полная замена значений, набора порций и признака архива
  под `expected_revision`. Возврат из архива — та же правка с `archived: false`.

Пример тела создания (новый UUID операции для каждого намеренного сохранения):

```json
{
  "operation_id": "10000000-0000-4000-8000-000000000001",
  "name": "Творог",
  "unit": "g",
  "protein": "10,00",
  "fat": "5",
  "carbohydrate": "0",
  "calories": null,
  "archived": false,
  "portions": [
    {"id": "20000000-0000-4000-8000-000000000001", "name": "Пачка", "quantity": "180"}
  ]
}
```

Все четыре показателя обязательны как поля, каждый допускает `null` и пустую
строку (неизвестно). Значения — десятичные строки с точкой/запятой, до сотых без
скрытого округления; завершающие нули допустимы. В БД — целые сотые, в ответе —
канонические строки с двумя знаками. Предел 2147483647 сотых, минимум 0;
количество порции строго больше 0. Числа JSON, bool, отрицательные, NaN/Infinity,
экспонента и лишняя точность отклоняются. Значения независимы, калории не
вычисляются. `unit` — `g` или `ml`, основа всегда 100; г ↔ мл не переводятся.

Названия продукта и порций обрезаются по краям, затем должны иметь 1–200 символов.
Одинаковые названия допустимы. UUID порций уникальны внутри карточки и устойчивы
при переименовании, изменении количества и перестановке; порядок задаётся массивом.
Отсутствующая в новом массиве порция убирается, самостоятельной ценности у порции нет.

Правка добавляет `expected_revision` (целое ≥1); при смене `unit` также обязательно
`unit_change_confirmed: true`, все четыре новых показателя и новый набор UUID
порций либо пустой массив. Старые UUID порций при смене единицы отклоняются.
Подтверждение в UI показывает новые значения и набор после очистки старых полей.

Карточка ответа содержит `id`, `name`, `unit`, четыре показателя, `portions`,
`archived`, `revision`, `created_at`, `updated_at` (RFC 3339, UTC, миллисекунды).
Создание/правка возвращают существующий формат квитанции: `operation_id`, `action`
(`create_product`/`edit_product`), `request_hash`, `result_id`, `revision`,
`completed_at`, `replayed`, `undo_remaining_ms: 0`. Карточка, порции и квитанция
атомарны. Повтор нормализованного запроса возвращает исходную квитанцию, затем
клиент перечитывает актуальный каталог. Старая квитанция не откатывает новые правки.

Ошибки имеют `{code, message, field}` без отражения значений запроса:

- 401 — нужен вход; 403 — неверный Origin/CSRF.
- 404 `not_found` — карточка отсутствует.
- 409 `operation_conflict` — UUID операции уже использован с другим содержимым,
  действием или карточкой; `revision_conflict` — устаревшая редакция.
- 422 `validation` — неверное поле; вложенное поле содержит индекс, например
  `portions.0.quantity`. 422 `unit_change` — нет подтверждения/нового набора порций.
- 413 — превышен лимит тела; 503 — ошибка БД, транзакция откачена.

При неопределённом результате клиент удерживает исходное тело и UUID в памяти
вкладки, повтор выполняется явно; вход не отправляет форму автоматически.
При 404/409/422/413 запрос разблокируется для исправления. После квитанции ошибка
чтения отличается от ошибки записи, повтор безопасен. Черновики и личные сведения
скрыты до входа; постоянного браузерного хранилища нет.

Миграция `005_products` добавляет только каталог и порции. Для реальной БД перед
миграцией нужна проверенная предмиграционная копия и совместимый релиз. Эта задача
проверяет только синтетические локальные БД; JSON версии 2 и чтение новых сущностей
при verify/restore запланированы отдельной задачей 06.
