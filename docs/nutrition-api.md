# API каталога и приёмов пищи

Все маршруты приватные и возвращают `Cache-Control: no-store`; запись требует
существующие cookie сессии, `Origin` и `X-CSRF-Token`. Названия, значения и UUID
операций передаются только в JSON-теле. Лимит тела — 65536 байт.

- `GET /api/products` — все карточки с полным упорядоченным
  набором порций; изначально `[]`. Поиск по подстроке без учёта регистра (включая
  кириллицу) выполняется клиентом; поискового параметра API нет.
- `GET /api/products/{id}` — текущая карточка; отсутствующая — 404.
- `POST /api/products` — создание. Сервер назначает UUID карточки и редакцию 1.
- `PUT /api/products/{id}` — полная замена значений и набора порций
  под `expected_revision`. Все сохранённые продукты доступны в каталоге.

Пример тела создания (новый UUID операции для каждого намеренного сохранения):

```json
{
  "operation_id": "10000000-0000-4000-8000-000000000001",
  "name": "Творог",
  "unit": "g",
  "protein": "10,00",
  "fat": "5",
  "carbohydrate": "0",
  "calories": null,
  "portions": [
    {"id": "20000000-0000-4000-8000-000000000001", "name": "Пачка", "quantity": "180"}
  ]
}
```

Все четыре показателя обязательны как поля, каждый допускает `null` и пустую
строку (неизвестно). Значения — десятичные строки с точкой/запятой, до сотых без
скрытого округления; завершающие нули допустимы. В БД — целые сотые, в ответе —
канонические строки с двумя знаками. Предел 2147483647 сотых, минимум 0;
количество порции строго больше 0. Числа JSON, bool, отрицательные, NaN/Infinity,
экспонента и лишняя точность отклоняются. Значения независимы, калории не
вычисляются. `unit` — `g` или `ml`, основа всегда 100; г ↔ мл не переводятся.

Названия продукта и порций обрезаются по краям, затем должны иметь 1–200 символов.
Одинаковые названия допустимы. UUID порций уникальны внутри карточки и устойчивы
при переименовании, изменении количества и перестановке; порядок задаётся массивом.
Отсутствующая в новом массиве порция убирается, самостоятельной ценности у порции нет.

Правка добавляет `expected_revision` (целое ≥1); при смене `unit` также обязательно
`unit_change_confirmed: true`, все четыре новых показателя и новый набор UUID
порций либо пустой массив. Старые UUID порций при смене единицы отклоняются.
Подтверждение в UI показывает новые значения и набор после очистки старых полей.

Карточка ответа содержит `id`, `name`, `unit`, четыре показателя, `portions`,
`revision`, `created_at`, `updated_at` (RFC 3339, UTC, миллисекунды).
Создание/правка возвращают существующий формат квитанции: `operation_id`, `action`
(`create_product`/`edit_product`), `request_hash`, `result_id`, `revision`,
`completed_at`, `replayed`, `undo_remaining_ms: 0`. Карточка, порции и квитанция
атомарны. Повтор нормализованного запроса возвращает исходную квитанцию, затем
клиент перечитывает актуальный каталог. Старая квитанция не откатывает новые правки.

Ошибки имеют `{code, message, field}` без отражения значений запроса:

- 401 — нужен вход; 403 — неверный Origin/CSRF.
- 404 `not_found` — карточка отсутствует.
- 409 `operation_conflict` — UUID операции уже использован с другим содержимым,
  действием или карточкой; `revision_conflict` — устаревшая редакция.
- 422 `validation` — неверное поле; вложенное поле содержит индекс, например
  `portions.0.quantity`. 422 `unit_change` — нет подтверждения/нового набора порций.
- 413 — превышен лимит тела; 503 — ошибка БД, транзакция откачена.

При неопределённом результате клиент удерживает исходное тело и UUID в памяти
вкладки, повтор выполняется явно; вход не отправляет форму автоматически.
При 404/409/422/413 запрос разблокируется для исправления. После квитанции ошибка
чтения отличается от ошибки записи, повтор безопасен. Черновики и личные сведения
скрыты до входа; постоянного браузерного хранилища нет.

Миграция `005_products` добавляет только каталог и порции. Для реальной БД перед
миграцией нужна проверенная предмиграционная копия и совместимый релиз. Эта задача
проверяет только синтетические локальные БД; JSON версии 2 и чтение новых сущностей
при verify/restore запланированы отдельной задачей 06.

## Приёмы пищи из каталога

- `POST /api/meals` — создать приём; сервер назначает UUID приёма и редакцию 1.
- `GET /api/meals/{id}` — актуальный приём со всем составом, включая мягко удалённый.
- `PUT /api/meals/{id}` — заменить состав, время и категорию под `expected_revision`.
- `POST /api/meals/{id}/delete` и `/restore` — мягкое удаление и восстановление;
  тело `{operation_id, expected_revision}`. Отмена разрешена строго до
  `deleted_at + 30000` мс серверного времени; на границе — 409 `undo_expired`.
- `GET /api/nutrition-day?day=2026-10-19` — `{day, meals, totals}` за московский день.
  Все неудалённые приёмы без усечения; порядок — время события, создания, UUID.
  Начало дня включено, следующая полночь исключена.

Пример тела создания:

```json
{
  "operation_id": "30000000-0000-4000-8000-000000000001",
  "occurred_at": "2026-10-19T12:00:00.123+03:00",
  "category": "lunch",
  "lines": [{
    "id": "40000000-0000-4000-8000-000000000001",
    "kind": "product",
    "name": "Творог",
    "unit": "g",
    "quantity": "90",
    "basis_quantity": "100",
    "protein": "10",
    "fat": "5",
    "carbohydrate": "20",
    "calories": "180",
    "product_id": "50000000-0000-4000-8000-000000000001",
    "product_revision": 1,
    "portion": {"id": "60000000-0000-4000-8000-000000000001", "name": "Пачка", "quantity": "180"}
  }]
}
```

`category` — `null` либо `breakfast`, `lunch`, `dinner`, `snack`. Время: RFC 3339
с явным смещением, до миллисекунд. Неизменённое время при правке отправляется
с исходной точностью, даже если форма показывает минуты. Для неоднозначного
местного времени используется существующий `/api/moscow-time`.

Состав непустой; порядок задаётся массивом. Клиентские UUID строк уникальны внутри
приёма и сохраняются при правке. Строка — самостоятельный исторический снимок:
название, единица `g`/`ml`, положительное съеденное количество, основа `100.00`,
четыре nullable-показателя на эту основу, происхождение продукта и необязательная
историческая порция. Порция заполняет количество, но не ограничивает его. Единица
количества совпадает с основой; перевода г ↔ мл нет. Входные количества/показатели
имеют числовые правила и пределы каталога. Сервер валидирует снимок и не заменяет
его текущей карточкой: она могла измениться после выбора. Правка снимка меняет
только этот приём. Клиентские итоги не принимаются.

Ответ: `id`, `occurred_at`, `category`, `revision`, `created_at`, `updated_at`,
`deleted_at`, `lines`, `totals`. Строки возвращают исходные поля и `totals`
из четырёх nullable-десятичных строк. Заголовок/строки/квитанция сохраняются одной
транзакцией. Действия: `create_meal`, `edit_meal`, `delete_meal`, `restore_meal`.
`undo_remaining_ms` выдаётся для удаления; повтор не продлевает срок. Старые
квитанции не меняют данные: клиент перечитывает актуальный приём и текущий день,
включая возможное последующее удаление.

`totals` приёма/дня содержит для каждого из `protein`, `fat`, `carbohydrate`,
`calories` объект `{value, known_count, unknown_count, incomplete}`. `value` — сумма
известных вкладов либо `null`, если известных нет; `incomplete` означает наличие
неизвестных строк именно этого показателя. День без еды: пустой состав, `null`,
счётчики 0, `incomplete: false`; UI показывает «Нет записей еды». Известный ноль
остаётся `0.00`, неизвестное не превращается в ноль.

Исходные величины хранятся целыми сотыми. Расчёт точный рациональный: значение на
100 × количество / 100. Half-up до сотых применяется независимо к строке, приёму
и дню. Две строки по 50 г с углеводами 0,01 г на 100 г показывают по 0,01 г,
вместе — 0,01 г. Произведения и итоги могут превышать предел отдельного поля.
Калории не вычисляются из БЖУ. Предпросмотр UI использует целочисленную арифметику;
итоги сохраняемого приёма сервер рассчитывает самостоятельно.

422 указывает индекс/поле, например `lines.1.quantity`, без отражения пищевых
данных в сообщении. Доступ, 413/503, конфликты и безопасные повторы соответствуют
каталогу. Черновик, конфликт и запрос живут в памяти вкладки при навигации и
повторном входе, до входа скрыты. Повтор только явный. Общая отмена доступна
между разделами, переход её срок не продлевает.

Миграция `006_meals` сохраняет прежнюю историю и каталог. Для рабочей БД нужна
проверенная предмиграционная копия совместимым со старой схемой релизом.
Текущий [полный экспорт v3](export/README.md) включает всё питание и
мягкие удаления. Проверка восстановления читает новые сущности и расчёты
приложения; номер схемы текущего релиза — `010_remove_product_archive`.

## Разовая еда и повтор

`lines` допускает смешанный состав `product` и `one_off`. У разовой строки нужны
`id` (UUID), `kind: "one_off"` и непустое `name`; четыре показателя, `quantity`
и `unit` необязательны. При количестве нужна единица `g`/`ml`. Происхождение
`product_id`, `product_revision`, `portion` должно отсутствовать либо быть `null`.
Числовые правила и пределы прежние. Пустой состав по-прежнему отклоняется.

Показатели разовой еды заданы за всю исходную порцию. При первом вводе
`basis_quantity` опускают: сервер сохраняет в нём исходное `quantity` либо `null`.
В ответе основа всегда явная. При правке/повторе клиент передаёт её без изменений,
независимо от нового количества. Известная основа позволяет точный пересчёт
`показатель × quantity / basis_quantity`; неизвестная (`null`) оставляет значения
целой порции даже при новом весе. Для иной порции пользователь явно исправляет
показатели либо вводит достоверное исходное количество в `basis_quantity`.
При известной основе обязательны единица и съеденное количество. Округление
строки, приёма и дня остаётся независимым, неизвестное не становится нулём.

- `GET /api/meals/{id}/repeat-form` возвращает `{occurred_at, category, lines}`
  из неудалённого исторического приёма, иначе 404. Время берётся с сервера
  при открытии (UTC с миллисекундами), строки получают новые UUID. Сохраняются
  порядок, снимки, исходные количества и основы, продуктов каталога.
  Маршрут ничего не записывает. Изменения источника после ответа не меняют
  полученный черновик. Только явный `POST /api/meals` с новым `operation_id`
  создаёт самостоятельное событие; повтор запроса использует прежний UUID.
- `POST /api/meal-product-preview`: `{line, unit, basis_quantity?}`. `line` —
  разовая строка без `totals`. При известной основе используется она и та же
  единица; иначе нужно фактическое количество исходной порции в `basis_quantity`.
  Новый съеденный вес при неизвестной основе не используется вместо неё.
  Ответ `{name, unit, protein, fat, carbohydrate, calories}` содержит значения
  на 100, округлённые half-up до сотых. Неизвестные остаются `null`.
  Без основы, при неверной единице или превышении предела карточки — 422.
  Предпросмотр не создаёт карточку и не изменяет приём. После проверки пользователь
  явно сохраняет ответ обычным `POST /api/products`, добавив `operation_id`
  и `portions: []`. Альтернатива — независимо заполнить пустую новую карточку.

В UI создание карточки доступно у строки черновика и истории. Отмена не мешает
записи и повтору еды. Повтор показывает текущее серверное время открытия, сохраняет
его до явной правки и допускает изменение состава/категории/количеств. Все
механизмы удержания черновика, ошибок, конфликтов и безопасного повтора общие.
Миграция `007_one_off_meals` переносит существующие строки без изменения фактов.

## Вода и кнопки

Вода независима от продуктов и приёмов; объём — JSON integer в целых мл,
1–2147483647. Дробь, строка, boolean и ноль отклоняются. Сумма дня может
превышать предел отдельного события. Напитки в мл не создают воду или наоборот.

- `POST /api/water`: `{operation_id, volume_ml, occurred_at?}`. Без времени
  (либо с `null`) сервер назначает текущий момент под транзакцией. Быстрая кнопка
  всегда использует этот вариант, независимо от выбранного дня. Другой момент
  задаётся явно RFC 3339 со смещением, до миллисекунд.
- `GET /api/water/{id}` возвращает `{id, volume_ml, occurred_at, revision,
  created_at, updated_at, deleted_at}`; время — UTC RFC 3339. Мягко удалённое
  событие доступно для проверки актуального состояния.
- `PUT /api/water/{id}` требует `{operation_id, expected_revision, volume_ml,
  occurred_at}`; время обязательно. Перенос меняет принадлежность московскому дню.
- `POST /api/water/{id}/delete` и `/restore` принимают обычный `RevisionInput`.
  Восстановление доступно строго при серверном elapsed < 30000 мс. Квитанция
  удаления содержит остаток срока; старый повтор не продлевает его.
- `GET /api/water-settings`: `{volumes_ml: [200,250,500], revision: 1}` в новой БД.
  Настройки общие для устройств. `PUT` принимает `{operation_id,
  expected_revision, volumes_ml}` — полный упорядоченный уникальный набор, включая
  пустой. Правка не меняет историю. Квитанция использует постоянный UUID настроек
  `00000000-0000-0000-0000-000000000001` и действие `edit_water_settings`.
- `GET /api/nutrition-day?day=…` дополнен `water` (все неудалённые события,
  порядок occurred_at/created_at/UUID) и `water_total_ml` (integer либо `null`
  при отсутствии записей). Вода и еда читаются в одной транзакции снимка.

Мутации возвращают общую квитанцию с действиями `create_water`, `edit_water`,
`delete_water`, `restore_water`, `edit_water_settings`. Одинаковые нормализованные
тело и UUID возвращают прежний результат; другой запрос с тем же UUID — 409.
После квитанции клиент перечитывает актуальное событие/настройки и выбранный день,
поэтому старый ответ не возвращает удалённое или последующие старые значения.
Все изменения атомарны с квитанцией; редакция проверяется под BEGIN IMMEDIATE.

Общие сессия, Origin/CSRF, no-store, 65536 байт и 401/403/409/413/422/503 действуют
для всех маршрутов. Ошибки полей: `volume_ml`, `occurred_at`, `volumes_ml` либо
`volumes_ml.N`. В интерфейсе ввод целых мл и настройка кнопок проверяются до
отправки; сервер остаётся обязательной границей проверки.

Миграция `008_water` создаёт воду и настройки без изменения прежних записей,
повторный upgrade безопасен. Миграция рабочей БД требует проверенной копии.
Экспорт воды/настроек v2 и проверка восстановления входят в задачу 06, не в 04.

## Сводки питания

`GET /api/nutrition-summary?period=week|month|custom&start=YYYY-MM-DD&end=YYYY-MM-DD`
— приватный маршрут с общими сессией и `Cache-Control: no-store`.
По умолчанию `week`, конец — сегодня по `Europe/Moscow`. `week`/`month` задают
последние 7/30 календарных дней включительно до `end`; `start` для них игнорируется.
Для `custom` начало обязательно, конец по умолчанию сегодня. Обе даты включены;
временной интервал — от московской полуночи начала до полуночи после конца,
правая граница исключена. История не ограничена 30 днями. Некорректные даты,
обратный порядок и выход вычисленных границ за календарь дают 422 с полем.

Ответ: `{start, end, food_days, meal_count, averages, days}`. `days` содержит
все даты по возрастанию, включая пустые: `{day, meal_count, totals}`.
`totals` имеет прежний формат дневных итогов по четырём показателям. `food_days`
считает дни хотя бы с одним неудалённым приёмом, даже полностью неизвестным.
Вода не влияет на итоги, число приёмов или дней с едой.

Для каждого показателя в `averages` возвращается
`{value, known_days, incomplete_days, incomplete}`. Сумма точных известных вкладов
делится на число дней с хотя бы одним известным значением этого показателя;
известный ноль входит в знаменатель. Пустые и полностью неизвестные дни не входят.
`value` — десятичная строка, независимо округлённая half-up до сотых, либо `null`
без известных дней. `incomplete_days` считает дни с едой и хотя бы одной неизвестной
строкой показателя, включая дни вне знаменателя; `incomplete` равно наличию таких
дней. Без еды оба счётчика 0, значение `null`, неполнота `false`.

Контрольный пример: 10 г + неизвестное, полностью неизвестный и пустой дни дают
`food_days: 2`, углеводы `{value: "10.00", known_days: 1, incomplete_days: 2,
incomplete: true}`. Добавление дня с известным нулём даёт знаменатель 2 и `"5.00"`.
Расчёт читает сохранённые строки продуктов и разовой еды одним запросом в
транзакции снимка, без обращения к актуальному каталогу и без промежуточного
округления дней. Правка, перенос, удаление и восстановление учитываются при чтении.

UI показывает границы, число приёмов/дней с едой, отдельные знаменатели и неполноту
текстом, дневные итоги и переход к истории нужного дня с сохранением черновика.
Подтверждённые операции с едой обновляют текущую сводку; повторный вход, возврат
в раздел и явное обновление перечитывают её. Поздние ответы прежнего периода или
чтения до мутации не заменяют текущие. Загрузка, пустой период и ошибка различимы.

### Фотография продукта

Необязательное поле `photo` содержит `data:image/jpeg;base64,...` до 45 000
символов либо `null`. Разрешён только JPEG с корректным base64 и сигнатурой;
внешние URL и SVG отклоняются. UI преобразует JPEG/PNG/WebP до 10 МБ
в миниатюру до 480 пикселей. Поле возвращается в каталоге и полном экспорте.
При PUT явный `null` убирает фото, отсутствие поля сохраняет прежнее фото
для совместимости со старыми клиентами. Для существующей БД нужна миграция
`009_product_photos`; старые карточки получают `null`.

Миграция `010_remove_product_archive` убирает прежний признак архивирования.
Все карточки и порции сохраняются; ранее скрытые продукты становятся доступными.
В текущем API поля `archived` нет. Полный экспорт выдаётся в версии 3;
контракты прежних файлов сохранены отдельно.
