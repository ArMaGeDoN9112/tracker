# Резервирование и восстановление

Все команды выполняются из корня проекта через Docker Compose. VPS уже есть, но его
окружение не проверено; внешний провайдер не выбран. По указанию пользователя
20 октября 2026 сейчас работаем только локально. Локальный репозиторий позволяет
проверить механизм, но не защищает от потери VPS. До реальных данных обязательно
повторить учение на независимом внешнем хранилище и записать результат ниже.

## Конфигурация

Создайте приватные `.local/backup.env`, `.local/backup-secrets/restic-password` и `.env`.
Пароль restic — длинный случайный секрет; не передавайте его аргументом команды.
Каталог секретов и файлы доступны только владельцу/UID 10001 контейнера (0700/0600).
Для локального учения содержимое `.local/backup.env`:

```dotenv
RESTIC_REPOSITORY=/repository
RESTIC_PASSWORD_FILE=/run/backup-secrets/restic-password
```

Для внешнего S3 используйте `RESTIC_REPOSITORY=s3:https://endpoint/bucket/diary`,
`AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY` в этом приватном файле. Он читается
Compose, не выводите `docker compose config` и `docker inspect` в общие журналы.
Схема URI определяет внешний транспорт; администратор обязан проверить, что конечное
хранилище независимо от VPS (в том числе для rclone, REST и SFTP).
Ключ restic и реквизиты хранилища сохраните отдельно у владельца, например в менеджере
паролей с независимой резервной копией. Потеря ключа делает репозиторий бесполезным.

`.env` содержит конфигурацию приложения для восстановления. Если необходимые
приложению секреты лежат в другом env-файле, укажите его через `DIARY_RECOVERY_CONFIG`
в `.env`; он войдёт в зашифрованный снимок как `recovery.env`. Ключ restic и доступ
к хранилищу туда помещать не нужно. `.local`, `.env` исключены из Git и образов.

```sh
docker compose build --build-arg DIARY_RELEASE=<git-commit-or-release-tag> backup
docker compose run --rm -T backup restic init
docker compose run --rm -T backup
docker compose run --rm -T backup restic snapshots
docker compose run --rm -T backup python -m diary.backup --database /data/diary.sqlite3 verify
```

`init` нужен только для нового репозитория. Для местного репозитория заранее создайте
`.local/restic` с правом записи UID 10001. Для production вместо `development` нужен
точный релиз из сохранённого Git/образа; его исходники и frontend должны оставаться
доступными владельцу отдельно от VPS. `DIARY_RELEASE` можно закрепить в `.env`.

Точка входа `python -m diary.backup` вызывает CLI из `diary/interfaces/cli/backup.py`.
Сценарии `diary/application/backup.py` управляют шагами через порт, адаптер
`diary/infrastructure/backup.py` выполняет SQLite/files/restic. Экспорт читает
единый снимок через `ExportDiary`; общий сериализатор `diary/interfaces/export.py`
используется HTTP и проверкой резервной копии. Все новые модули входят в bundle
вместе с пакетом `diary`; формат JSON и команды не меняются.
Полная [структура бэкенда](architecture.md) описывает сборку и классы сценариев;
возврат прежнего кода после этого переноса не требует обратной миграции БД.

Команда использует SQLite Online Backup API, проверяет integrity/foreign keys и чтение
текущими DTO приложения. Снимок включает всю SQLite (включая служебные таблицы и
удаления), schema/release/SQLite version, Python/backend-исходники и миграции,
lock-файлы Python/Node, Dockerfile/Compose/Caddyfile и recovery.env. Manifest содержит
SHA-256 каждого файла; контроль снимается с копии, а не с меняющейся живой БД.
Для схемы `012_meal_type` валидатор читает через общий сборщик экспорта v5 все карточки
и порции, приёмы со строками/историческими основами и
расчётами (включая удалённые), воду и упорядоченные уникальные кнопки.
Проверяются обязательный непустой состав, UUID, исходные основы, DTO и связи;
историческое происхождение строки не требует актуальной карточки/порции.
Повреждение новых данных отклоняет backup/readback/verify, время прежнего
успешного verify сохраняется. Формат manifest и группа `diary-v1` не меняются.
Промежуточные файлы имеют приватные права, удаляются после штатного выхода. После
жёсткого завершения процесса администратор удаляет оставшиеся `diary-backup-*`/
`diary-verify-*` из приватного тома, убедившись, что процесс не работает.

Точка помечена `pending`, пока обратное скачивание и проверка не прошли. Непроверенные
точки не участвуют в автоматическом восстановлении latest, недельной проверке или
ротации; администратор разбирает их отдельно. Успех записывается только после проверки.
Хост restic фиксирован как `diary`, группа — `diary-v1`, daily/manual/premigration
разделены. После успешной ежедневной копии остаются семь последних успешных московских
дней, одна точка в день; пропуски не сокращают число точек до семи календарных дней.
Повтор за день сохраняет последнюю точку. `forget` удаляет только выбранные daily ID,
затем `prune` освобождает блоки; manual/premigration не вытесняют daily и автоматически
не удаляются. Каждая точка логически полная и включает старую историю.

Перед миграцией используйте отдельную проверенную точку:

```sh
docker compose run --rm -T backup python -m diary.backup --database /data/diary.sqlite3 backup --kind premigration
```

Команду до миграции выполняет **релиз, совместимый с исходной схемой**.
Текущий релиз проверяет только `012_meal_type`; для снимка `004_temporary_basal`
нужен соответствующий прежний релиз. Сначала проверьте предмиграционную точку
старым релизом, затем выполните явную миграцию новым и создайте новую проверенную
копию. Старт приложения миграций не выполняет; новую схему старым приложением
не открывайте. Номер JSON-экспорта 3 не заменяет Alembic revision и manifest version.

Ручная точка: `--kind manual`. `--at RFC3339` предназначен для учений с управляемыми
датами; на рабочем расписании его не используйте. Одновременные команды блокируются
flock на общем томе. Restic дополнительно блокирует репозиторий. После аварии restic
не выполняйте `unlock`, пока не убедитесь, что других процессов нет.

## Независимый планировщик

Шаблоны `ops/diary-{backup,verify}.{service,timer}` рассчитаны на Linux/systemd и проект
`/opt/diary`. При развёртывании исправьте WorkingDirectory/путь docker под реальный VPS,
установите файлы в `/etc/systemd/system`, выполните `systemctl daemon-reload` и
`systemctl enable --now diary-backup.timer diary-verify.timer`.
Ежедневно в 03:00 Europe/Moscow выполняется backup; по воскресеньям в 05:00 — полное
чтение блоков `restic check --read-data` и восстановление latest в новый временный
каталог с контрольными данными и чтением сериализаторами приложения. Persistent=true
повторяет пропущенный запуск после включения. Пересечение запусков даёт ошибку:
после её устранения повторите команду. Это не фоновые задачи FastAPI.

Проверьте `systemctl list-timers`, пробный `systemctl start diary-backup.service`,
`journalctl -u diary-backup.service -u diary-verify.service` и повтор после перезагрузки.
В журнал попадает только результат без stdout/stderr restic, реквизитов и данных.
Если systemd недоступен, нужен эквивалент с повтором пропуска и тем же общим томом.

В настройках видны внешний/локальный успех отдельно, последняя успешная проверка,
ошибки последнего запуска и проверки. Отсутствие внешнего успеха за 26 часов вызывает
предупреждение; статус загружается при открытии страницы без фонового опроса. После прерывания остаётся
«Запуск ещё не завершён». Файл состояния хранится рядом с БД отдельно от неё;
восстановление старой SQLite не выдаёт старый статус за современный успех. При полной
недоступности VPS интерфейс предупредить не сможет. Внешние уведомления не настроены.

## Восстановление без потери текущих записей

1. Остановите запись: `docker compose stop front back`. Не запускайте приложение до
   окончания переключения. Если текущая БД доступна, сохраните отдельную manual-точку
   приведённой командой. При недоступности репозитория сохраните текущее состояние
   через Online Backup API в другом приватном месте; без такой копии не переключайте.
2. Выберите ID через `restic snapshots`. Из manifest выбранной точки узнайте релиз и
   схему: `restic dump <ID> /manifest.json`. Используйте совместимый сохранённый релиз
   (checkout/образ); не пытайтесь открыть новую схему старым приложением.
3. Восстановите в **новый** каталог на томе, не поверх рабочей БД:

   ```sh
   docker compose run --rm -T backup python -m diary.backup --database /data/diary.sqlite3 restore --snapshot <ID> --target /data/recovered-point
   ```

   Существующий каталог отклоняется. После загрузки проверяются SHA-256/схема,
   integrity/foreign keys и чтение приложением. Сессии и предварительные CSRF-сессии
   отзываются в восстановленной SQLite, живая БД не меняется. Manifest отражает снимок
   **до** этого намеренного отзыва. Ошибка оставляет каталог для разбора, но не переключает БД.
4. В закрытом изолированном окружении с совместимым релизом проверьте новый вход и отказ
   старой cookie, все сущности, удаления, исторические границы базы, сводки и экспорт.
   Сверяйтесь с контрольными данными выбранной точки, а не с более новой живой БД.
   Зафиксируйте дату, ID, release/schema, результат и длительность без секретов.
5. Сохраните старую БД и её WAL/SHM при остановленных процессах. Настройте `DIARY_DATABASE`
   сервиса back на `/data/recovered-point/diary.sqlite3` в приватном Compose override
   (либо переместите старые файлы в отдельный приватный каталог и переключите проверенный
   файл). Права UID 10001/0600 обязательны. Укажите тот же новый путь в командах backup
   и systemd; не оставляйте резервирование старой БД. Восстановите recovery.env приватно,
   сверив домен/пути; не печатайте его в журнал. Запустите совместимый релиз и проверьте вход.
6. Новые записи после выбранной точки остаются в сохранённом текущем состоянии для
   отдельного решения владельца. Автоматического слияния/уничтожения этих записей нет.
   Проведите новую внешнюю копию и verify. Повторяйте учение после изменения схемы.

## Допуск и ограничения проверки

Автотесты используют синтетическую БД со всеми текущими сущностями схемы `012_meal_type` и настоящий
локальный зашифрованный restic. Проверяются чтение во время записи, восстановление,
отзыв сессий, ротация с управляемыми датами, раздельные виды копий, смена окружения,
недоступность/неверный ключ и смоделированные ошибки загрузки. Это не доказательство
внешней доставки, реального заполнения диска, поведения сети или таймеров на VPS.
Учение включает карточку и порции до/после смены основы, исторические строки,
разовую еду с/без количества, ноль/неизвестность, переносы/удаления, воду и кнопки.
После восстановления авторизованный API сравнивает весь экспорт (кроме
`exported_at`), дни и сводки. Отдельно проверяются конкурентная правка состава
и отказ при неверных новых данных/связях/основах/схеме. Фактические команды
локальной приёмки и итоговые результаты: [архитектура](architecture.md#проверки).

Перед допуском с реальными данными остаются: независимый внешний репозиторий, проверка
реквизитов при условной полной потере VPS, учение на внешней точке в чистом окружении,
фактическое время восстановления, реальные сбои сети/диска, установка/перезапуск таймеров
и права файлов на VPS. Добавляйте покрытия новых схем вместе с их миграциями.
Семь точек не заменяют бессрочную рабочую историю и не защищают от ошибки, пережившей
всю ротацию. Неизменяемость хранилища не настроена; доступ с VPS к удалению может
позволить злоумышленнику удалить и резервные точки.

Эти условия допуска сохраняют требования [общей спецификации](../.scratch/tracker/spec.md);
локальная приёмка архитектуры их не закрывает.
