# Clean Architecture для бэкенда

До перехода HTTP, SQL и правила операций совмещались в модулях
функциональности. Чтобы тестировать правила и сценарии без HTTP и реальной БД,
бэкенд разделён на `domain`, `application`, `infrastructure` и `interfaces`,
с группировкой по функциям проекта внутри каждого слоя. Внутренние слои
не импортируют внешние; Pydantic разрешён для типизированных данных и валидации,
чтобы сохранить принятую в проекте модель DTO без параллельной конвертации.
DTO сценариев принадлежат application и переиспользуются HTTP, когда смысл
и поля совпадают; разные представления получают разные DTO.

Каждый сценарий application оформляется отдельным классом с явно переданными
зависимостями, включая простые операции; это сознательный выбор единой формы
вместо сочетания функций и классов. DI-фреймворк не требуется.
Зависимости, включая часы и генерацию ID, передаются в конструктор;
`execute` принимает входной DTO и возвращает типизированный результат.
Ожидаемые отказы выражаются типизированными исключениями без HTTP-статусов;
внешние адаптеры сохраняют прежние ответы и не раскрывают внутренние ошибки.
Application задаёт границы операций через интерфейс Unit of Work и использует
интерфейсы хранения под нужды сценариев. Реализация SQLite управляет соединением,
блокировкой и commit/rollback; изменение данных и квитанция UUID атомарны,
составные чтения используют единый снимок.

Переход поэтапный для всего бэкенда, включая HTTP, admin CLI и резервирование,
с сохранением API, данных SQLite, экспорта, команд и поведения. Фронтенд
не входит в рефакторинг. Порядок: общие типы и расчёты, вода, дневник и база,
продукты и питание, графики и сводки, экспорт и резервирование, доступ и admin.
Приёмка сочетает проверки ядра без БД, интеграционные SQLite, API-регрессию
и автоматический контроль зависимостей; запуск через Docker Compose.
Все этапы переноса выполнены. Текущая структура, полный перечень сценариев,
границы зависимостей и проверки описаны в [архитектуре](../architecture.md).
