# Личный дневник диабета

Реализованы задачи 01–07: личный доступ, быстрый ввод, просмотр московского дня, исправление, перенос и мягкое удаление записей с отменой, суточное расписание базы, история его версий, создание, исправление и завершение временной базы с удалением и отменой, графики и сводки сахара.

## Запуск через Docker Compose

Нужны Docker Engine с Compose v2 либо Docker Desktop в режиме Linux containers.
Python, Node.js, uv и браузеры на компьютере устанавливать не требуется.
Все команды ниже выполняются из корня репозитория и одинаковы для PowerShell, Linux и macOS.
Зависимости устанавливаются по `uv.lock` и `frontend/package-lock.json`.

Для новой пустой БД:

```sh
docker compose build back front
docker compose run --rm back python -m diary.admin --database /data/diary.sqlite3 migrate
docker compose run --rm back python -m diary.admin --database /data/diary.sqlite3 create-account --login owner
docker compose up -d --wait
```

Введите пароль дважды в интерактивном терминале. Ввод скрыт; длина 15–1024 символа,
вставка разрешена. Пароль не передаётся флагом или переменной окружения.
Для создания аккаунта и смены пароля сохраняйте интерактивный TTY: не добавляйте `-T`.
Повторное создание аккаунта отклоняется.

Откройте **https://localhost:5173**. Frontend — собранный React в Caddy, backend —
FastAPI/Uvicorn в отдельном контейнере. `/api/*` проксируется на `back:8000`
с исходным Host; порт backend наружу не публикуется. Caddy выдаёт локальный сертификат:
для разработки подтвердите исключение браузера. Его локальный CA и сертификаты
сохраняются в томе `caddy_data`; корневой сертификат можно получить командой:

```sh
docker compose cp front:/data/caddy/pki/authorities/local/root.crt ./diary-local-root.crt
```

При необходимости импортируйте этот сертификат в доверенные корневые сертификаты ОС/браузера.
HTTP **http://localhost:8080** перенаправляет на точный HTTPS-origin.
Cookie всегда `Secure`, `HttpOnly`, `SameSite=Lax`, с префиксом `__Host-`, без `Domain`.

Проверка состояния, журналы, обновление исходников и остановка:

```sh
docker compose ps
docker compose logs --tail 100 back front
docker compose up -d --build --wait
docker compose down
```

`up --build` пересобирает образы после правок; автоматической перезагрузки исходников нет.
`down` сохраняет тома. **Не используйте `down -v` для данных, которые нужно сохранить:**
эта команда удаляет SQLite и локальный CA. SQLite находится в `diary_data` по пути
`/data/diary.sqlite3`, вне образа и публичной статики. Backend работает от UID 10001.
Схема создаётся только административной миграцией; старт приложения её не создаёт.
Frontend запускается после успешной проверки готовности backend.

### Настройки и доступ с телефона

Для изменения параметров скопируйте `.env.example` в `.env` и отредактируйте его.
`.env` исключён из Git и контекста сборки. По умолчанию порты доступны только на loopback.
Для доверенной локальной сети, например для компьютера `192.168.1.10`:

```dotenv
DIARY_HOST=192.168.1.10
DIARY_ORIGIN=https://192.168.1.10:5173
DIARY_BIND=0.0.0.0
DIARY_HTTPS_PORT=5173
DIARY_HTTP_PORT=8080
DIARY_TLS=internal
```

После изменения выполните `docker compose up -d --wait`. Телефон открывает указанный HTTPS-origin;
нужен доверенный локальный CA или подтверждение сертификата. Фактический iPhone/Safari пока не проверен.
`DIARY_HOST` — только имя/IP без схемы и порта; `DIARY_ORIGIN` — точный HTTPS-origin без пути
и завершающего `/`. Для стандартного HTTPS-порта 443 не добавляйте `:443` к origin.

### Перенос существующей локальной SQLite

Новый Docker-том не подхватывает прежний файл `data/diary.sqlite3` автоматически.
Сначала остановите прежний backend. Следующая команда предназначена только для **пустого**
тома: она откажет, если целевая БД уже существует. Исходная БД открывается только для чтения,
копирование выполняется SQLite Backup API, исходный файл сохраняется.

```sh
docker compose run --rm --user root --volume ./data:/import:ro back python -c "import os, sqlite3; from pathlib import Path; target = Path('/data/diary.sqlite3'); assert not target.exists(), 'Target database already exists'; source = sqlite3.connect('file:/import/diary.sqlite3?mode=ro', uri=True); destination = sqlite3.connect(target); source.backup(destination); destination.close(); source.close(); os.chown(target, 10001, 10001)"
docker compose run --rm back python -m diary.admin --database /data/diary.sqlite3 migrate
docker compose up -d --wait
```

Перед миграцией рабочей БД нужен проверенный согласованный снимок.
Перезапуски, пересборки и повтор `migrate` сохраняют данные; именованный том не заменяет внешнюю копию.

## Смена пароля и отзыв сессий

В интерактивном терминале, пока Compose-приложение запущено:

```sh
docker compose exec back python -m diary.admin --database /data/diary.sqlite3 reset-password
```

Новый хеш и удаление всех сессий фиксируются одной транзакцией. Неудачная операция откатывается. Для проверки:

1. Войдите в двух браузерах или на телефоне и компьютере.
2. Выйдите на одном устройстве: второе сохраняет вход.
3. Снова войдите на обоих и выполните `reset-password`.
4. В каждом браузере обновите страницу: старые cookie получают 401, появляется форма входа. Старый пароль отклоняется, новый позволяет войти.

После пяти ошибок за 15 минут блокируются новые проверки пароля по источнику **или** логину. Отказ 429 с `Retry-After: 900` не продлевает блокировку; после выхода ошибок из скользящего окна вход доступен. Счётчики хранятся в SQLite. Неизвестный логин и неверный пароль дают одинаковый ответ.

## API и общая защита

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/auth/csrf` | Получить `{csrf_token}` для текущей сессии либо предварительную cookie на 15 минут. |
| `POST /api/auth/login` | JSON `{login, password}`; возвращает `{login, csrf_token}` и новую cookie на 30 дней. Логин: 1–128 символов после удаления крайних пробелов; пароль: до 1024 символов, без преобразования. |
| `GET /api/auth/session` | `{login}` для действующей сессии; иначе 401. |
| `POST /api/auth/logout` | Отозвать текущую сессию; 204 и удаление cookie. |

Для POST обязательны точный `Origin` и `X-CSRF-Token`, полученный через `/csrf`. Предварительный токен после входа недействителен; новый связан с новой сессией. Значения сессий и предварительных cookie случайны (32 байта), в БД только SHA-256. CSRF получается из случайного токена с отдельным префиксом. Серверный срок сессии фиксирован от входа и не продлевается чтением. Повторный вход отзывает прежнюю сессию этого устройства.

Весь FastAPI защищён middleware по умолчанию. Исключения — только точные пары метода и пути `/csrf` и `/login`. Новые предметные маршруты автоматически требуют сессию и для изменений Origin/CSRF. Не создавайте отдельный незащищённый API. Публичная статика не содержит данных владельца. CORS не включён; документация `/docs`, `/redoc`, `/openapi.json` отключена во всех окружениях.

Ответы имеют `Cache-Control: no-store`. Ошибки: `{code, message, field}` без введённых значений; статусы 401, 403, 422, 429, 503, а также 400 для неверного Host и 413 для тела свыше 64 КиБ. SQLite использует внешние ключи, `synchronous=FULL`, ожидание блокировки до 10 секунд. Вход и восстановление пароля сериализованы `BEGIN IMMEDIATE`. Ошибка БД не объявляется успехом. Тела запросов, пароли, cookie и SQL-параметры не журналируются; access-log Uvicorn отключён в инструкции.

## Проверки

### Графики и сводки сахара

`GET /api/glucose-summary?period=week|month|custom&start=YYYY-MM-DD&end=YYYY-MM-DD`
возвращает фактические `start`, `end`, общее `count`, среднее `average` и `days`
с полями `day`, `count`, `average`, `minimum`, `maximum`. Значения сахара — десятичные
строки в ммоль/л; без измерений — `null` и число 0.
Неделя и месяц включают последние 7 и 30 московских календарных дней до `end`
включительно; без `end` используется сегодня по Москве. Для `custom` требуется `start`.
Неверные или непредставимые границы дают 422. Сессия обязательна, ответы не кэшируются.

Сводки учитывают все неудалённые измерения периода, включая многолетнюю историю;
подколки, комментарии и база не влияют на число измерений. Средние считаются из
целых десятых с half-up только в результате; среднее периода взвешено по всем измерениям.
График Recharts оставляет разрывы на пустых днях, различает линии штрихами и показывает
число измерений на правой оси. Доступная таблица содержит те же значения и кнопки
перехода к дню с клавиатуры. После сохранения, переноса, удаления и отмены сводка перечитывается.

### Быстрый ввод и день

После входа форма получает время сервера и показывает его в `Europe/Moscow`, независимо от зоны устройства. Время остаётся выбранным до сохранения; его можно изменить вручную. Повторяющееся историческое время требует выбора смещения UTC, несуществующее отклоняется. До настройки расписания база неизвестна (`null`), включая состояние на начало дня.

`POST /api/entries`: `{operation_id, occurred_at, glucose?, bolus?, reason?, comment?}`. `operation_id` — UUID, `occurred_at` — RFC 3339 с явным смещением и точностью до миллисекунд. Числа передаются строками: точка/запятая, точность до десятых (завершающие нули допустимы), технический максимум 214748364,7. Сахар положительный либо `null`; пустая подколка равна нулю. Причины: `food`, `correction`, `food_and_correction` либо `null`; при нуле причина очищается. Комментарий — обычный текст до 10 000 символов. Нужны сахар, ненулевая подколка или непустой комментарий.

Квитанция содержит UUID операции, `result_id`, редакцию, время выполнения и `replayed`. Запись и квитанция фиксируются вместе. Тот же UUID с нормализованным содержимым возвращает исходную квитанцию; иное содержимое — `409 operation_conflict`. При неизвестном результате форма удерживает данные и UUID, ограничивает изменение полей и предлагает ручной повтор. После ответа перечитывает день. Черновик переживает повторный вход в этой вкладке, но не перезагрузку страницы; автоматической отправки и офлайн-очереди нет.

`GET /api/day?day=YYYY-MM-DD` возвращает все записи московского дня без ограничения первой страницей, по времени события, создания и UUID. Числа — строки с одним знаком после точки, времена — UTC RFC 3339. `GET /api/entry-form` получает начальное московское время с сервера; `GET /api/moscow-time?local_time=YYYY-MM-DDTHH:mm` возвращает допустимые абсолютные моменты для локального времени. Все эти маршруты закрыты общей проверкой сессии. Модели запросов и ответов доступны через `create_app(...).openapi()` программно; публичный HTTP OpenAPI отключён.

### Исправление и удаление записей

`GET /api/entries/{id}` возвращает актуальную запись, включая `revision` и `deleted_at`; доступ требует входа, включая чтение удалённой записи для сравнения при конфликте.

`PUT /api/entries/{id}` принимает те же поля, что создание, и обязательную `expected_revision`. Это полная замена редактируемых полей с прежней валидацией; `created_at` сохраняется. Форма отправляет исходную точную метку события, пока пользователь не изменил отображаемую минуту. Перенос сразу меняет хронологию обоих дней; сводки будут добавлены задачей 07.

`POST /api/entries/{id}/delete` и `POST /api/entries/{id}/restore` принимают `{operation_id, expected_revision}`. Все изменения сериализованы `BEGIN IMMEDIATE`: проверка редакции и состояния, изменение и квитанция находятся в одной транзакции. Успех увеличивает редакцию на один. Несовпадение редакции или состояния — `409 revision_conflict`; отсутствующая запись — `404 not_found`. Интерфейс предлагает загрузить актуальную запись рядом с введёнными значениями. Продолжить с собственными значениями можно только явным действием; повторная конкурентная правка снова даст конфликт.

Удаление сохраняет данные бессрочно и сразу исключает их из дня. Восстановление разрешено только при серверном `now < deleted_at + 30000`; ровно на границе — `409 undo_expired`. В квитанции удаления `undo_remaining_ms` показывает оставшийся серверный срок, в остальных — 0. Кнопка отмены доступна с клавиатуры и исчезает по таймеру; окончательное решение всегда принимает сервер. В открытой вкладке предлагается отмена последнего удаления.

UUID, действие, идентификатор записи и нормализованное содержимое определяют повтор. Совпадение возвращает исходную квитанцию даже после истечения срока отмены; квитанция описывает результат той операции, а не текущую редакцию. Повтор создания не воскрешает удалённую запись, повтор восстановления не изменяет более поздние данные. После квитанции интерфейс перечитывает день. Неизвестный результат сохраняет исходный запрос и UUID для ручного повтора, включая удаление и восстановление и повторный вход. Перезагрузка вкладки теряет этот черновик и кнопку отмены.

Схема 002 уже содержит редакции, удаления и квитанции; дополнительной миграции для задачи 03 нет. Повтор `migrate` и перезапуск сохраняют эти поля и безопасные повторы.

### Суточное расписание базы

`POST /api/basal-schedules` принимает `{operation_id, starts_at, intervals: [{minute, rate}]}`:
начало — RFC 3339 со смещением, минута — целое 0–1439, скорость — десятичная строка
в ед/ч с точностью до сотых (точка или запятая, завершающие нули разрешены).
Первый интервал обязателен с 00:00; последующие начала строго возрастают.
Технический максимум скорости — 21474836,47 ед/ч, это предел хранения, не медицинский диапазон.

Каждая версия полная, неизменяемая и хранится бессрочно. Она действует от своего начала
включительно до следующей версии исключительно; до первой версии база неизвестна (`null`).
Можно сохранить будущую или историческую версию. Историческая вставка уточняет базу
уже внесённых событий только в своём периоде; база не копируется в записи.
`GET /api/basal-schedules` возвращает всю историю, интервалы и вычисленные `ends_at`.
Занятое начало возвращает `409 schedule_conflict`, `existing_id` и ссылку `href` на версию
в интерфейсе. Редактирования и удаления версий нет. Общие сессия/CSRF и атомарные квитанции
защищают создание; повтор с теми же нормализованными данными возвращает исходный результат.

`GET /api/basal?at=<RFC3339>` вычисляет базу для выбранного момента формы.
День содержит `basal` на московскую полночь и `basal_changes` с моментами изменений;
каждая запись содержит базу для собственного времени. Все скорости — строки с двумя
знаками. Точные границы, исторические смещения Москвы и повторяющиеся часы учитываются
по Europe/Moscow. Интерфейс показывает единицы и подпись «по расписанию», предварительный
просмотр затрагиваемого периода и отдельную историю. Черновик и UUID неопределённого
результата остаются в памяти вкладки при потере сети и повторном входе.

Миграция 003 добавляет версии и интервалы, сохраняя прежние записи, сессии и квитанции.
HTTP-проверки включают обновление со схемы 002, сбои транзакции и конкуренцию;
браузер проверяет исторический день, потерю ответа и конфликт начала.

### Временная база

`POST /api/temporary-basals` принимает `{operation_id, starts_at, duration_minutes, percent}`.
Начало — RFC 3339 со смещением, длительность — целое от 1 до 2147483647 минут,
процент — целое от 0 до 2147483647. Это технические пределы формата, не рекомендации.
Заданное окончание должно помещаться в календарь UTC и Europe/Moscow.
`GET /api/temporary-basals` возвращает неудалённые периоды по началу: UUID, `starts_at`,
заданное `ends_at`, вычисленное `effective_ends_at`, исходные `duration_minutes`, `percent`,
`created_at`, `updated_at`, `revision` и `deleted_at`. Времена передаются с миллисекундами UTC.

Эффективное окончание — минимум заданного окончания и следующего неудалённого начала.
Интервалы полуоткрытые; новая временная база прекращает предыдущую без возобновления.
Историческая вставка не меняет заданные окончания соседей. Одинаковое начало даёт
`409 temporary_conflict`; создание и квитанция повтора атомарны в `BEGIN IMMEDIATE`.
Миграция 004 добавляет таблицу и уникальный индекс неудалённых начал, сохраняя историю.

Процент применяется к текущему интервалу текущей версии расписания, включая московскую
полночь. Итог округляется до сотых half-up: 0,55 × 110% = 0,61 ед/ч. Результат может
превышать предел хранимой скорости; вычисляется без переполнения целого и без float.
Неизвестная база остаётся `null`, в том числе при 0%. `GET /api/day` дополнительно содержит
пересекающие день `temporary_basals` и `temporary_percent` на начало дня (`null` означает
обычное расписание). Начала и эффективные окончания отражены в `basal_changes`, даже
если скорость не меняется. Форма показывает заданное и эффективное окончания, а также
период до максимума нового окончания и прежнего эффективного окончания предшественника.
После сохранения перечитываются день и скорость формы. Фонового задания и расчёта
фактически введённой дозы нет.

`PUT /api/temporary-basals/{id}` принимает `{operation_id, expected_revision, starts_at, ends_at, percent}`.
Меняются начало, заданное окончание и процент; исходная длительность и время создания сохраняются.
Окончание можно исправить задним числом или задать равным началу (нулевой период), но не раньше него.
`POST /api/temporary-basals/{id}/delete` и `/restore` принимают `{operation_id, expected_revision}`.
Удаление мягкое; восстановление доступно строго до `deleted_at + 30000` мс по времени сервера.
Квитанция удаления содержит `undo_remaining_ms`; повтор возвращает исходную квитанцию,
а интерфейс перечитывает актуальное состояние. `GET /api/temporary-basals/{id}` позволяет
прочитать также удалённую запись для сравнения; история её сохраняет.

Проверка редакции, занятости начала, изменение и квитанция атомарны в `BEGIN IMMEDIATE`.
Устаревшая редакция даёт `409 revision_conflict`, занятое начало при правке или отмене —
`409 temporary_conflict`, истёкшая отмена — `409 undo_expired`. Соседние окончания
пересчитываются при чтении, исходные заданные окончания не обрезаются в БД.
Перед подтверждением форма показывает затрагиваемый период, включая изменившиеся границы
соседей. Конфликт сохраняет ввод и предлагает актуальную запись для сравнения.
Неопределённый результат удерживает запрос и UUID для ручного повтора; после перезагрузки
вкладки черновик и кнопка отмены теряются. Дополнительная миграция для задачи 06 не требуется.

### Полный JSON-экспорт

В настройках после входа доступен «Экспорт всех данных»: прямое скачивание
`GET /api/export` с проверкой сессии и `Cache-Control: no-store`.
Файл содержит всю историю, включая мягко удалённые данные, в одном снимке SQLite.
Десятичные строки и RFC 3339 сохраняют исходную точность; единицы указаны в файле.
Описание каждого поля, JSON Schema v1 и пример: [документация экспорта](docs/export/README.md).
Секреты и квитанции не включены; пользовательского импорта нет.

### Запуск проверок

```sh
docker compose run --build --rm checks
docker compose run --rm checks mypy
docker compose build front
docker compose run --build --rm e2e
```

`checks` содержит dev-зависимости Python; сборка `front` включает TypeScript и Vite.
`e2e` содержит Python, Node.js и Chromium; Playwright сам запускает одноразовые API и HTTPS Vite
внутри своего контейнера. Том рабочей БД не подключается, синтетический аккаунт удаляется
вместе с временной SQLite. Сервисы проверок не запускаются обычным `up`; профили включать
вручную не нужно, если сервис указан в `compose run`. Отчёты по умолчанию остаются в одноразовом
контейнере; скриншоты и трассировки с секретами не сохраняются.

HTTP-тесты используют временные файловые SQLite, реальные миграции и Argon2id. Часы подменяются только для проверки точных границ сроков. Проверяются перезапуск, повтор миграции, ротация, выход, смена пароля, CSRF/Origin, общий запрет доступа, ограничения по IP и логину, поддельный `X-Forwarded-For` и одновременные попытки.

Playwright сам запускает API с одноразовой SQLite и синтетическим аккаунтом, а также HTTPS Vite. Порты 8000 и 5173 используются только внутри контейнера `e2e` и не конфликтуют с запущенным приложением. Сценарий выполняется в Chromium для настольного и мобильного размеров: вход, перезагрузка, выход с клавиатуры, повторная перезагрузка; проверяет cookie и отсутствие localStorage. Это эмуляция размера экрана, не проверка Safari или реального iPhone. Скриншоты, видео и трассировка с секретами не сохраняются.

Проверки записей охватывают варианты ввода и валидацию, исторические московские границы, стабильный большой список, повтор и конфликт UUID, конкурентные запросы, сбои commit/нехватку места/блокировку на границе SQLAlchemy, перезапуск и повтор миграции. Браузер работает в `America/Los_Angeles` и проверяет запятую, отдельные поля, текст без HTML, выбор смещения, потерю ответа после commit и повторный вход без скрытого сохранения.

## Production

Используется тот же `compose.yaml`: `front` отдаёт только собранную статику через Caddy,
`back` не публикует порт. На VPS нужны Docker Engine/Compose v2 и постоянный локальный диск
для Docker-томов; Python и Node.js на хосте не нужны. Для домена с публичным DNS пример `.env`:

```dotenv
DIARY_HOST=diary.example.com
DIARY_ORIGIN=https://diary.example.com
DIARY_BIND=0.0.0.0
DIARY_HTTPS_PORT=443
DIARY_HTTP_PORT=80
DIARY_TLS=owner@example.com
```

Замените домен и email своими. При доступных извне 80/443 и правильном DNS Caddy запрашивает
и продлевает публичный TLS-сертификат; `DIARY_TLS=internal` используется только для локальной проверки.
Если порты уже заняты, до запуска согласуйте схему с существующим прокси.
Настройка реального домена/VPS автоматически не выполняется.

Первоначальное создание аккаунта и миграции выполняются командами из раздела запуска.
Для обновления существующей БД сначала подготовьте проверенный снимок, затем:

```sh
docker compose build back front
docker compose stop front back
docker compose run --rm back python -m diary.admin --database /data/diary.sqlite3 migrate
docker compose up -d --wait
```

Backend работает без root и без доверия к `X-Forwarded-*`; все запросы через Caddy имеют
общий источник для ограничения входа, а ограничение по логину действует отдельно.
Не включайте доверие ко всем адресам `*`. SQL-параметры, тела запросов и access-log отключены.
`restart: unless-stopped` восстанавливает сервисы после перезапуска Docker, если они не были
остановлены вручную. Состояние Docker и свободное место тома требуют контроля на фактическом VPS.

VPS, внешнее резервирование и проверенное восстановление остаются задачами 09–12.
Перед первыми реальными данными нужны независимые внешние копии и успешное восстановление
согласно спецификации; наличие Compose этого не заменяет.
