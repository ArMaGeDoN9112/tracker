## Реализация

`GET /api/export` выдаёт v2: прежние сущности, все карточки/порции/архив,
приёмы с самостоятельными историческими основами и расчётами, воду, кнопки,
редакции/время/мягкие удаления. Использованы действующие DTO и сериализаторы.
Общий сборщик вызывается в явном SQLite-снимке и из проверки резервной БД.
Расчёты исторических строк не требуют актуальной карточки/порции.

Проверка снимка сохраняет integrity/FK, manifest/SHA-256 и совместимость релиза
с Alembic head `008_water`. Неверные новые сущности/основы/связи/настройки
не становятся успешным verify. Механизм restic, pending, новый каталог,
отзыв сессий, статусы и ротация не заменены. Новых миграций в этой задаче нет.

Опубликованы [схема v2](../../docs/export/schema-v2.json),
[пример v2](../../docs/export/example-v2.json), [описание](../../docs/export/README.md).
Сохранены схема/пример v1 и точное прежнее описание в `README-v1.md`.
Обновлены API, действующие правила продукта и инструкция восстановления;
предмиграционную копию старой схемы проверяет совместимый прежний релиз.

## Что проверяют HTTP и локальный restic

- DTO/JSON Schema/пример v2 согласованы; описание/пример/схема v1 сохранены.
  Приватность, `no-store`, attachment, истёкшие/отозванные сессии остаются проверены.
- Архив содержит всю историю независимо от query дня/limit: архивную карточку
  после смены г → мл и порций, прежнюю строку с прежней основой и порцией,
  разовую еду с/без количества, неизвестное и ноль, перенесённые/удалённые
  приёмы/воду, пользовательский порядок кнопок. Историческая строка из JSON
  повторно даёт прежние расчёты через API при изменённом каталоге.
- Два управляемых конкурентных сценария при чтении порций/строк: независимый
  клиент меняет карточку с порциями, состав, создаёт новый многострочный приём
  и меняет кнопки. Весь экспорт равен снимку до правок, последующий — после.
- Настоящий restic: backup → readback → restore → verify на схеме `008_water`.
  Восстановленный полный экспорт равен исходному, исключая только `exported_at`;
  дни дневника/питания, сводки сахара/питания и кнопки совпадают через API.
  Переносы, удаления, старая диабетическая история и новые сущности включены.
  Восстановленные сессии отозваны; исходная БД и записи после точки сохранены.
- Копирование при непрерывной правке двухстрочного состава восстанавливает
  согласованную редакцию, обе строки и соответствующий итог.
- Повреждённые архивный продукт/порция/происхождение строки, основа, связь,
  пустой состав, удалённая вода, кнопки и несовместимая schema revision
  отклоняются. Тест пересчитывает SHA-256 повреждённой синтетической копии,
  чтобы проверить содержимое после manifest, а не только контрольную сумму.
  Время и ID прежнего успешного verify остаются прежними.
- Прежние проверки семи успешных московских дней, manual, pending, неверного
  ключа, недоступного репозитория, прерывания/имитации нехватки места и блокировки
  параллельных команд входят в полный backend-набор.
