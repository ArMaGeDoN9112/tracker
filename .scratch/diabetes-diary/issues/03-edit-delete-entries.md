# 03: Исправление и удаление записей

**What to build:** пользователь исправляет запись, переносит её в другой день, удаляет ошибочную и может отменить удаление, не затирая изменения с другого устройства.

**Blocked by:** 02.

**Status:** resolved

**Type:** task

- [x] Редактируются сахар, подколка, причина, комментарий и время события с прежней серверной валидацией; время создания и точность не редактировавшихся меток сохраняются.
- [x] Перенос меняет хронологию обоих дней. Когда доступны сводки, правки, перенос, удаление и восстановление сразу отражаются в затронутых днях и периодах.
- [x] Изменение, удаление и восстановление атомарно проверяют ожидаемую редакцию и увеличивают её. Из двух конкурентных изменений одной редакции проходит только одно; проигравшему предлагается загрузить актуальную запись с сохранением введённых значений для сравнения.
- [x] Удаление мягкое и сразу исключает запись из обычного просмотра. Отмена доступна строго до истечения 30 секунд по серверному времени, после чего данные остаются для экспорта и резервирования. Кнопка доступна с клавиатуры.
- [x] Все операции имеют атомарные квитанции и безопасные повторы. Поздний повтор создания не воскрешает удалённую запись, повтор восстановления не затирает последующие изменения.
- [x] HTTP-проверки используют независимые соединения с одной SQLite для гонок и управляемое время для границы 30 секунд. Браузерный сценарий покрывает перенос, удаление, отмену и конфликт двух устройств; перезапуск и миграция сохраняют редакции и удаления.

## Answer

Добавлены чтение отдельной записи, полная правка редактируемых полей, перенос между московскими днями, мягкое удаление и восстановление. Время создания сохраняется; форма удерживает точность исходного времени события при изменении других полей. Конфликт редакций позволяет загрузить актуальную запись рядом с введёнными значениями и явно выбрать дальнейшее редактирование.

Все операции используют общую `BEGIN IMMEDIATE` транзакцию проверки редакции/состояния, изменения и записи квитанции. Повтор сверяет UUID, действие, ID записи и нормализованные поля; возвращает исходную квитанцию без повторного изменения данных. Позднее создание не воскрешает удалённую запись, повтор восстановления не затирает последующие правки. Схема 002 уже содержит все нужные поля, новой миграции нет.

Отмена разрешена строго до `deleted_at + 30000` по серверному времени. Кнопка последнего удаления доступна с клавиатуры; медленное получение CSRF до удаления не сокращает её срок. Черновики и запросы с неизвестным результатом сохраняются в памяти вкладки, повторы требуют нажатия пользователя. После квитанции день перечитывается; оба дня переноса читаются из актуальных записей. Сводки пока отсутствуют и относятся к задаче 07.

Проверки: полный набор из 69 HTTP-тестов (25 новых), mypy, TypeScript и production-сборка; 12 браузерных сценариев desktop/mobile Chromium. Покрыты независимые конкурентные соединения к одной SQLite, строгая граница 29 999/30 000/30 001 мс, сбои commit и квитанции, безопасные поздние повторы, перезапуск и повтор миграции. Браузер проверяет перенос, отмену с клавиатуры, конфликт двух устройств, потерю ответов после commit каждой операции и сохранение исходных миллисекунд.

Решения: [Decisions-so-far](../map.md#decisions-so-far). Контракт API: [README](../../../README.md#исправление-и-удаление-записей).

### Standards

Ревью обнаружило гонку отмены редактирования с сохранением. Исправлена общей блокировкой отправки; браузер проверяет задержку, ошибку загрузки формы и сохранение черновика. После повторного ревью оставшихся замечаний нет.

### Spec

Ревью обнаружило сокращение видимого срока отмены на время запроса до удаления. Отсчёт перенесён на получение серверного остатка; сценарий с продвижением часов браузера во время получения CSRF проверен на desktop/mobile. Сервер всегда проверяет окончательную границу отдельно. После повторного ревью оставшихся замечаний нет.

Реальные iPhone/Safari и VPS не проверялись. Перезагрузка вкладки теряет черновик и кнопку отмены; сами записи, удаления и квитанции остаются в БД. Экспорт, сводки и резервирование относятся к последующим задачам.
