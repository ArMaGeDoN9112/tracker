# Дневник диабета — первая версия

Status: ready-for-agent

Дата: 19 октября 2026 года. Это техническая спецификация первого этапа. Пользователь выбрал FastAPI и согласовал три границы проверок: HTTP API с настоящей SQLite, ключевые браузерные сценарии и эксплуатационное восстановление. Реализация этим документом не начинается.

## Problem Statement

Пользователю нужно быстро записывать сахар, подколки и комментарии с iPhone и компьютера, видеть выбранный день и изменения сахара за период. Бумажные записи трудно анализировать. Важно не потерять многолетнюю историю, правильно показывать базу для времени события и закрыть личные данные от посторонних.

Дневник ведёт один человек через интернет. Он самостоятельно интерпретирует внесённые данные; сервис не рекомендует дозы инсулина и не подтверждает фактическую подачу помпы.

## Solution

Личный веб-дневник с паролем, сохранением входа на устройствах и адаптивным интерфейсом с приоритетом тёмной темы. Главное действие — быстрый ручной ввод: сахар в фокусе, текущее московское время заполнено, подколка и комментарий необязательны, база показана по расписанию для выбранного момента.

Пользователь настраивает одно суточное расписание базы, сохраняет его изменения с датой начала действия и вносит временную базу в процентах. В истории доступны записи дня и графики дневного среднего, минимума, максимума и числа измерений. Данные хранятся бессрочно, доступны полный JSON-экспорт и ежедневное резервирование всей истории отдельно от VPS с последними семью копиями.

## Implementation Decisions

### Исходное состояние и объём изменения

- В репозитории есть согласованные продуктовые требования, карта интервью, словарь и инструкции для агентов. Кода приложения, зависимостей, тестов, конфигурации развёртывания и ADR пока нет; переиспользовать существующие программные модули или тестовые границы невозможно.
- Предстоит создать только дневник диабета: доступ, записи, расписания, временную базу, просмотр, экспорт и эксплуатационные команды. Для них нужны схема БД и миграции, API-контракты, React-интерфейс, проверки и инструкция эксплуатации. Универсальные сущности событий, плагины, шина сообщений и заготовки следующих модулей не нужны.
- Продуктовые правила и термины исходной спецификации и словаря имеют приоритет. Ниже явно выбраны технические детали, оставшиеся открытыми после интервью; это решения данной спецификации, а не приписанные пользователю ответы.

### Минимальный стек

- Бэкенд: FastAPI, Pydantic для проверки входных данных, синхронный SQLAlchemy для SQLite, Alembic для миграций, Uvicorn для запуска. Один процесс приложения достаточен для первой версии; корректность операций обеспечивается БД, а не числом процессов.
- Фронтенд: React, TypeScript, Vite, React Router для экранов и Recharts для графика. Семантические HTML-элементы и общие стили покрывают формы и тёмную тему. Отдельный сервер рендеринга, глобальное хранилище состояния и генератор компонентов не требуются.
- В production React собирается в статические файлы; браузер и API работают с одного HTTPS-домена. Node.js нужен для сборки, но не как второй сервер приложения. По требованию пользователя приложение запускается через Docker Compose: `back` — FastAPI/Uvicorn, `front` — Caddy со статической сборкой React и прокси `/api/*`. На хосте нужны Docker Engine и Compose v2; Python и Node.js находятся в образах. Существующий веб-сервер и порты VPS проверяются до развёртывания.
- Зависимости закреплены в `uv.lock` и `frontend/package-lock.json`; Dockerfile использует Python 3.12, Node.js 22 и Caddy 2. Миграции, создание аккаунта, смена пароля, HTTP/типовые и браузерные проверки запускаются через Compose по README. Миграции выполняются явно; запуск приложения не меняет схему.
- SQLite хранится в именованном Docker-томе `diary_data` (`/data/diary.sqlite3`) на постоянном локальном диске вне образа и публичной статики. Обычный `docker compose down` сохраняет том; `down -v` удаляет его и не применяется к сохраняемым данным. Включены внешние ключи, надёжная синхронизация записи и короткие транзакции. Записи, затрагивающие временные границы или несколько сущностей, сериализуются транзакцией с ранним получением блокировки записи; нельзя полагаться на блокировку строки, которой SQLite не предоставляет.
- Блокировка БД, нехватка места и ошибка фиксации возвращают ошибку сохранения без частичных изменений. WAL допустим после проверки окружения, но не заменяет резервирование. Сетевой диск для рабочей SQLite не используется.
- Обновление приложения не пересоздаёт БД. Перед миграцией создаётся проверенный снимок; миграции проверяются на существующих данных. Возврат старого кода допустим только при совместимости схемы, иначе применяется документированный порядок восстановления с явным учётом новых записей.

### Время и числовые значения

- Время события, начало действия расписания, начало и окончание временной базы — абсолютные моменты. Хранение в БД: целые миллисекунды UTC; API и экспорт: RFC 3339 с явным смещением. Временные метки без смещения отклоняются. Интерфейс переводит введённое московское локальное время в момент явно, независимо от часового пояса устройства.
- Единственная календарная зона дневника — `Europe/Moscow`. Не подменять её часовым поясом ОС, браузера или постоянной арифметикой UTC+3 для всей исторической шкалы. Несуществующее или неоднозначное историческое локальное время требует явного выбора смещения; тихое исправление недопустимо.
- По умолчанию форма получает текущее время сервера при открытии; до отправки выбранное время остаётся видимым и не меняется скрыто. Сервер отдельно назначает время создания и обновления. При редактировании время создания сохраняется.
- День — полуинтервал от московской полуночи включительно до следующей московской полуночи исключительно. Для периода обе выбранные календарные даты включены; верхняя техническая граница — начало следующего дня. Событие ровно в полночь относится к новому дню.
- Начала суточных интервалов хранятся как минуты местного времени от 00:00. Точность редактируемого времени в форме — минута; исходные метки не теряют точность при изменении других полей.
- Сахар хранится в десятых ммоль/л, подколка — в десятых единицы, скорость базы — в сотых ед/ч. Целочисленное хранение исключает накопление двоичной погрешности. В JSON API и экспорта значения передаются десятичными строками с точкой и фиксированными 1/1/2 знаками; интерфейс принимает точку и запятую.
- Сахар строго положительный, подколка и скорость неотрицательные. Пустая подколка и 0 нормализуются в 0. Отсутствующий сахар — `null`, не 0. Лишние значащие десятичные знаки отклоняются с подсказкой, а не округляются скрыто; завершающие нули допустимы.
- Процент временной базы — целое неотрицательное число; 0% разрешён, 100% означает обычную скорость. Значения, включая процент, ограничены технической вместимостью положительного 32-битного целого в своих единицах хранения. Это ограничение формата, не медицинский диапазон; клинические пороги и рекомендации не вводятся.
- Вычисленная скорость: обычная скорость × процент / 100, округление до сотых ед/ч по правилу half-up только в конечном результате. Например, 0,55 ед/ч × 110% = 0,605 → 0,61 ед/ч. База всегда отображается с двумя знаками, включая 0,00. Неизвестная база остаётся неизвестной и при 0%.

### Модель данных

Идентификаторы предметных сущностей — стабильные UUID. Индексы покрывают время события, начало действия расписания и начало временной базы. Связи и ограничения проверяются сервером и, где возможно, БД.

| Сущность | Данные и ограничения |
| --- | --- |
| Личный аккаунт | Единственная запись аккаунта, логин, хеш пароля, время создания. Публичной регистрации нет; одноразовое создание административной командой. |
| Сессия | Хеш случайного токена, связь с аккаунтом, время создания и истечения. Отдельная сессия на каждом устройстве. |
| Запись дневника | Время события, сахар либо `null`, подколка, необязательная причина, комментарий, время создания/обновления, номер редакции, время удаления либо `null`. База не копируется в запись как независимое значение. |
| Версия суточного расписания базы | Начало действия, время создания, набор интервалов. Начало действия уникально. Версии неизменяемы и сохраняются бессрочно. |
| Интервал расписания | Связь с версией, минута начала, скорость в сотых ед/ч. Для каждой версии обязателен 00:00; начала уникальны и возрастают, находятся в пределах суток. |
| Временная база | Начало, заданное окончание, исходная длительность в минутах, процент, время создания/обновления, номер редакции и признак удаления. Длительность при создании положительная. Фактическая граница действия вычисляется с учётом следующей временной базы. |
| Квитанция изменения | UUID операции, вид действия, хеш нормализованного запроса, идентификатор результата, итоговая редакция и время выполнения. Нужна для безопасного повтора операций после потери ответа. Не содержит паролей или токенов. |

- Одной записи достаточно сахара, ненулевой подколки или непустого после удаления крайних пробелов комментария. Причина без этих данных не делает запись содержательной. При нулевой подколке причина очищается; допустимые причины — еда, коррекция, еда и коррекция. По тексту комментария причина не выводится.
- Комментарий — обычный текст до 10 000 символов, без HTML и вложений. Он может содержать сведения о еде или активности, но структурированных сущностей для них нет.
- Время создания не используется вместо времени события ни в графиках, ни при выборе базы. При равном времени события порядок стабилен по времени создания и UUID.
- Предметные данные, версии расписаний и мягко удалённые записи не очищаются по возрасту. Бессрочное хранение не означает ведение всех редакций комментария или сахара: сохраняется актуальное состояние, видимая история правок не предусмотрена. Истёкшие сессии и технические журналы можно очищать отдельно.

### Суточное расписание и история базы

- Для момента события выбирается версия с наибольшим началом действия, не превышающим этот момент. Её конец — начало следующей версии, исключительно. Если подходящей версии нет, база неизвестна; первое расписание не распространяется на прошлое автоматически.
- В выбранной версии используется последний суточный интервал, начавшийся к местному времени события. Последний интервал заканчивается в следующую полночь. На точной границе действует новый интервал или новая версия.
- Изменение расписания создаёт полную новую версию с выбранным началом действия. Будущая или внесённая задним числом версия действует до следующей уже существующей версии. Перед сохранением показаны дата начала и затрагиваемый период; значения раньше выбранного начала не меняются.
- Существующие версии нельзя молча перезаписывать или удалять. В первой версии приложения отдельного редактора исправления сохранённой версии нет: изменение задаётся новой версией с другим началом действия. Попытка занять уже существующее начало возвращает конфликт и ссылку на эту версию. Это ограничение явно обозначается в интерфейсе истории расписаний.
- Добавление исторической версии намеренно уточняет расчёт базы в её периоде, включая уже внесённые записи. Позднейшая версия не переписывает более ранние периоды. Значение базы при просмотре рассчитывается из истории; отдельный снимок базы в каждой записи не хранится, чтобы исправление времени события не оставляло устаревшее значение.
- Хронология дня показывает записи и границы изменений базы; при входе в день видно состояние на его начало, даже если временная база началась вчера. История расписаний доступна отдельно с датами действия.

### Временная база

- При создании пользователь задаёт начало, положительную длительность в целых минутах и процент. Заданное окончание равно началу плюс длительность; досрочное завершение меняет заданное окончание. Исправление окончания задним числом разрешено, но окончание не может быть раньше начала; равенство означает нулевой период действия.
- Активные, не удалённые временные базы упорядочиваются по началу. Для каждой эффективное окончание — минимум её заданного окончания и начала следующей. Период полуоткрытый: начало включено, окончание исключено. Одинаковое начало двух временных баз отклоняется как конфликт.
- Новая временная база прекращает предыдущую с момента своего начала. После окончания новой предыдущая не возобновляется. Это справедливо и для внесения задним числом; изменение начала или удаление пересчитывает соседние границы в одной транзакции.
- Если временная база удалена, остаётся расписание либо другая временная база, которая действовала бы без удалённой записи. Перед таким исправлением показан затрагиваемый период; отмена удаления возвращает прежнее состояние. Операция не оставляет сохранённых вручную обрезанных окончаний у соседей.
- Процент применяется к обычной скорости в каждом конкретном моменте: при смене суточного интервала или версии расписания временная база продолжается с тем же процентом от новой скорости. Проценты никогда не перемножаются и не суммируются.
- До появления известного расписания временную базу можно записать, но вычисленная скорость неизвестна. По её окончании снова действует обычное расписание для соответствующего момента.
- Интерфейс различает заданное и эффективное окончание, если период прекращён новой временной базой. На границе одновременной смены расписания и начала временной базы используются новое расписание и новый процент.
- Расчёт не требует фонового задания в момент окончания: результат определяется временными границами при запросе. Временная база и обычная база подписаны «по расписанию», без обещания фактической подачи и без вычисления суммарной введённой базальной дозы.

### Сохранение, редактирование и удаление

- Сервер проверяет все поля независимо от фронтенда. Успех показывается только после фиксации транзакции; при ошибке форма остаётся заполненной. При потере сети отправка не маскируется под успешное сохранение, офлайн-очереди нет.
- Каждое предметное изменение получает UUID операции. Повтор с тем же UUID и тем же содержимым не выполняет изменение повторно; сервер возвращает квитанцию исходного результата. Другой запрос с тем же UUID — конфликт. Квитанция и изменение фиксируются атомарно; время события и UUID сохраняются при повторе после неопределённого результата.
- Это распространяется на создание, изменение, удаление, восстановление записей и управление базой. Квитанции сохраняются, чтобы поздний повтор создания не воскресил уже удалённую запись. После квитанции повтора клиент перечитывает актуальное состояние: исходный результат не выдаётся за новую редакцию.
- Редактирование, удаление и восстановление передают ожидаемый номер редакции. Устаревшая редакция возвращает конфликт без перезаписи; интерфейс предлагает загрузить текущую запись, сохраняя введённые пользователем значения для сравнения. Изменение и увеличение редакции атомарны.
- Удаление записи дневника или временной базы мягкое. В течение 30 секунд по серверному времени доступна кнопка «Отменить»; период не зависит от таймера браузера. Кнопка доступна с клавиатуры и достаточно долго видна. Повтор восстановления безопасен; восстановление с конфликтом соседних временных баз отклоняется с объяснением.
- После удаления запись сразу исключается из обычного просмотра и сводок. После отмены она возвращается и сводки обновляются. После 30 секунд обычной кнопки восстановления нет; удалённые данные остаются в полном экспорте и резервных копиях. Автоматического физического удаления нет.
- Просмотр и управление сохранёнными расписаниями следуют отдельным правилам неизменяемых версий выше; обещание редактирования и отмены удаления относится к записям дневника и временной базы.

### API-контракт и просмотр

- API предоставляет только вход/выход и состояние сессии, операции записей, чтение/создание версий расписания, операции временной базы, дневную хронологию, сводку периода и полный экспорт. Административное создание аккаунта и восстановление пароля не публикуются как HTTP-методы.
- Описание OpenAPI фиксирует поля, форматы, точность, обязательность, ограничения, перечисления, UUID операции и ожидаемую редакцию. Ошибки имеют стабильный код, понятное сообщение и указатель поля, когда применимо. Основные ответы: 401 при отсутствии входа, 403 при нарушении CSRF, 404 для отсутствующего объекта, 409 при конфликте, 422 при неверном вводе, 429 при ограничении входа и 503 при временной недоступности записи. Внутренние исключения и секреты в ответ не попадают.
- Дневная хронология возвращает события и состояние базы для их времени; график — календарную дату, число измерений, среднее, минимум и максимум каждого дня. Статистика считается сервером из не удалённых измерений, а не из состояния браузера. Большие списки можно читать страницами, но график и экспорт не ограничиваются первой страницей или последними 30 днями.
- Неделя и месяц — последние 7 и 30 календарных дней включительно с выбранной конечной датой; по умолчанию она сегодня по Москве. Произвольный период позволяет выбрать обе даты. Подписи показывают фактические границы.
- Среднее за день — сумма сахара / число измерений. Среднее периода — сумма всех сахаров / общее число измерений, без промежуточного округления дневных средних. Для отображения применяется half-up до одного знака; исходные значения не меняются.
- Без измерений число равно 0, среднее/минимум/максимум — `null`; на графике разрыв, без соединения через пустой день. При одном измерении все три значения совпадают. Подколки, комментарии и база не создают измерений сахара. Нажатие на день открывает его исходные измерения.
- График имеет текстовую таблицу с теми же значениями и доступный переход к дню; цвет не единственный носитель смысла. Изменение даты события переносит измерение и пересчитывает оба затронутых дня.

### Доступ и защита данных

- Единственный аккаунт создаётся локальной административной командой, повторное создание отклоняется. Пароль задаётся интерактивно без отображения и не попадает в аргументы процесса, журнал или репозиторий. Хеширование — Argon2id через `pwdlib`; самодельная криптография не используется. Пароль длиной 15–1024 символа, без обязательного набора классов символов, вставка и менеджеры паролей разрешены.
- Вход создаёт криптографически случайный непрозрачный токен не менее 256 бит. В БД хранится его хеш. Cookie — `Secure`, `HttpOnly`, `SameSite=Lax`, без общего домена для поддоменов, срок 30 дней от входа; сессия имеет такой же серверный срок. Идентификатор сессии заменяется при входе. Токены доступа не хранятся в localStorage.
- Каждый запрос данных, изменений и экспорта требует действующей сессии. Глобальное правило доступа применяется ко всем предметным маршрутам; случайно добавленный открытый маршрут недопустим. Клиентский роутер не является защитой данных. Документация API в production отключена либо также закрыта входом.
- Для всех изменяющих HTTP-запросов, включая вход и выход, проверяются разрешённый Origin и CSRF-токен. Для входа используется предварительный CSRF-токен, после успешного входа он обновляется и связывается с сессией. Одной настройки SameSite недостаточно. Читающие запросы не меняют предметные данные, CORS для посторонних origin не разрешается.
- Ограничение входа действует до дорогой проверки хеша: не более пяти неуспешных попыток за 15 минут по источнику и логину, с временным ограничением, без бессрочной блокировки аккаунта. Счётчики разделяются запросами и переживают перезапуск, например в SQLite; ответы не раскрывают существование логина. Доверять адресу клиента можно только от проверенного обратного прокси.
- Выход удаляет текущую сессию и cookie. Команда восстановления пароля меняет хеш и удаляет все сессии атомарно; старые cookie больше не работают. Инструкция включает проверку нового входа и отказа старой сессии. Почта не нужна.
- Принудительный HTTPS, проверка Host, корректное доверие заголовкам прокси, закрытый внутренний порт Uvicorn, запуск без root и отладочного режима. Публичны только нужные порты веб-сервера; SSH ограничен административным доступом. Секреты и БД доступны только необходимым системным пользователям.
- Комментарии выводятся как текст с экранированием. Для приватных ответов и JSON-экспорта используется `Cache-Control: no-store`; сервис-воркер с кэшированием дневника не создаётся. Пароли, cookie, тела записей, комментарии и содержимое экспорта не записываются в логи; сторонних трекеров и отправки данных внешним сервисам нет.

### Полный документированный JSON-экспорт

- Кнопка «Экспорт всех данных» находится в настройках. После проверки сессии сервер формирует согласованный снимок всех предметных данных на один момент, независимо от выбранного периода, пагинации и возраста записей. Файл скачивается непосредственно, не публикуется по общедоступной ссылке.
- Корень JSON содержит `schema_version`, `exported_at`, `timezone`, описание единиц и массивы записей дневника, версий расписания с интервалами и временной базы, а также настройки и несекретные данные аккаунта. Не существующие в первой версии каталоги не создаются ради формата будущих модулей.
- Для каждой сущности сохраняются UUID, предметные поля, времена создания/изменения, редакции и признак/время удаления. Для временной базы сохраняются заданное окончание, исходная длительность и процент; эффективное окончание при наличии приводится как производное. Неизвестные значения — `null`. Все версии расписания включены, даже если сейчас не действуют.
- Документация формата описывает каждое поле, единицы, точность, временную зону, полуоткрытые границы, причины подколки, правила удаления и расчёта временной базы. Она включает валидный пример, JSON Schema и правило увеличения версии при несовместимом изменении. Проверка экспорта использует эту схему и сравнивает данные с исходной историей.
- Хеши паролей, сессии, CSRF-токены, ключи резервирования, квитанции запросов и технические журналы в пользовательский экспорт не входят. Полнота относится ко всем пользовательским данным; JSON не является копией служебной БД.
- Экспорт включает мягко удалённые записи и явно предупреждает об этом рядом с кнопкой. Это позволяет сохранить полную накопленную историю; файл содержит личные сведения и передаётся только владельцу.
- Пользовательского импорта в первой версии нет. Восстановление сервиса выполняется из резервной копии; JSON обеспечивает переносимость и возможность проверить данные независимо от приложения, без обещания готового обратного импорта.

### Ежедневные резервные копии и восстановление

- Базовый инструмент — restic с зашифрованным репозиторием вне VPS, предпочтительно в отдельном S3-совместимом хранилище. Провайдер, регион, учётная запись, стоимость и доступ ещё не выбраны. Другая папка или другой диск того же VPS не удовлетворяют требованию.
- Один ежедневный запуск в 03:00 по Москве создаёт согласованный полный снимок SQLite через Online Backup API, проверяет целостность и внешние ключи, добавляет версию схемы/релиза, lock-файлы и воспроизводимые сведения о конфигурации восстановления. Прямое копирование работающего основного файла SQLite, особенно без WAL, запрещено.
- Снимок содержит всю накопленную БД, включая историю расписаний и мягко удалённые данные. Каждая точка restic является логически полной копией и восстанавливает всю историю без последовательного применения предыдущих ежедневных снимков; дедупликация блоков внутри репозитория не сокращает содержимое снимка. Отдельные самостоятельные файлы по одному на день не обещаются.
- Планировщик — системный timer с повтором пропущенного запуска после включения, если это поддерживает VPS; иначе эквивалентный доступный планировщик. Ограничение одного одновременного запуска обязательно. Работа резервирования не зависит от посещения сайта и фоновых задач процесса FastAPI.
- После успешной загрузки и проверки читаемости сохраняются семь последних успешных ежедневных точек дневника, не семь последних календарных дней. В один московский день остаётся одна ежедневная точка; ручные и предмиграционные копии учитываются отдельно и не вытесняют ежедневные. Для restic задаётся стабильная группа дневника, не меняющаяся с именем хоста или релизом. На этапе накопления их меньше семи.
- Удаление старых точек запускается только после успешной новой копии и её проверки; при сбое выгрузки ротация не выполняется. Проверяется и освобождение неиспользуемых блоков, иначе удаление записей снимков не ограничит расход хранилища. Политика применяется только к выделенным ежедневным копиям этого дневника.
- Рабочие секреты не публикуются. Зашифрованная резервная копия включает необходимые для восстановления конфигурационные секреты, но ключ расшифрования restic и реквизиты доступа к внешнему хранилищу должны дополнительно храниться у владельца отдельно от VPS и от самой зашифрованной копии. До запуска проверяется доступ к ним при условной полной потере VPS.
- В настройках видны время последней успешной внешней копии, последней успешной проверки восстановления и ошибка последнего запуска без секретов. При сбое показывается предупреждение; при отсутствии успешной копии более 26 часов — предупреждение о просрочке. Логи планировщика сохраняют результат для администратора. Внешний канал уведомлений не считается настроенным без отдельного выбора; при полной недоступности VPS интерфейс предупредить не сможет.
- При исправном ежедневном резервировании целевая потеря данных при аварии — не более последних суток. При пропущенных копиях гарантия нарушена, что явно отражается в статусе. Время полного восстановления не обещается до измерения на реальном окружении.
- До реального использования выполняется восстановление внешней копии в чистое изолированное окружение с доступом только администратора. Проверяются целостность БД, схема, количества и содержимое сущностей, исторические границы, дневные сводки, экспорт и новый вход. Восстановленные сессии удаляются, чтобы старые токены не ожили после отката.
- После запуска автоматическая проверка восстановления выполняется не реже раза в неделю: загрузить последнюю внешнюю точку, восстановить в отдельное место, проверить БД и контрольные данные и запустить минимальную проверку чтения приложением. Она не заменяет рабочую БД и не публикует восстановленные данные. Полная проверка чтения блоков репозитория также выполняется еженедельно; проверка структуры без чтения данных недостаточна.
- Для обычного восстановления документируется порядок: прекратить запись, сохранить доступное текущее состояние отдельно, выбрать точку и совместимый релиз, восстановить в новое место, проверить и только затем переключить приложение. Если живая БД доступна, автоматический откат с уничтожением новых записей недопустим. Учение повторяется после изменения схемы или механизма копирования.
- Семь точек восстановления не заменяют бессрочное хранение рабочей истории. Ошибка или исправление, обнаруженные после смены всех копий, могут быть невосстановимы; история всех редакций записей не ведётся. Доступ с VPS к удалению копий также означает, что компрометация VPS может затронуть резервный репозиторий; неизменяемое хранилище не заявляется настроенным.

### Интерфейс

- Основные экраны: вход, быстрый ввод/день, графики, расписание и его история, временная база, настройки с экспортом и состоянием копий. На телефоне приоритет быстрому вводу, на компьютере — также истории и графикам. Дизайн спокойный, без игровых наград и балла здоровья.
- Тёмная тема по умолчанию, контрастные подписи и видимый фокус. Основные интерактивные области не меньше 44 × 44 CSS-пикселей, нет горизонтальной прокрутки формы на узком экране. Поля имеют настоящие подписи и сообщения об ошибках; управление доступно с клавиатуры.
- Сахар и подколка используют подходящую десятичную клавиатуру iPhone. Дата и время явно подписаны как московские. При невозможности автоматического фокуса на iOS поле остаётся первым и доступным одним нажатием; реальное поведение проверяется на устройстве.
- Подписи единиц и базы «по расписанию» видны рядом со значениями. Успех, ошибка, сохранение и возможность отмены различимы текстом, а не только цветом. Состояние отправки предотвращает повторное нажатие, но серверная защита повторов всё равно обязательна.

## Testing Decisions

### Согласованные границы

- Пользователь подтвердил три границы после выбора FastAPI: HTTP API с настоящей SQLite; небольшой набор браузерных сценариев; эксплуатационное восстановление. Новых согласований по этим границам не требуется.
- Основная граница — HTTP API через pytest и FastAPI TestClient с отдельной файловой SQLite и настоящими миграциями. Тестируются наблюдаемые ответы и последующее чтение, а не имена функций, SQL-запросы или устройство React-компонентов. Авторизацию, CSRF, расчёт базы и репозитории не подменять заглушками. Для гонок используются независимые соединения с одной тестовой БД.
- Браузерные проверки — Playwright с запущенными React и FastAPI и отдельной тестовой БД. Мобильный размер и WebKit полезны, но не заменяют ручной тест Safari на настоящем iPhone. Все медицинские значения в тестах синтетические.
- Эксплуатационная граница — команды резервирования/восстановления с настоящим тестовым внешним хранилищем, а перед запуском — выбранное рабочее хранилище и VPS. Тесты приложения не доказывают корректность TLS, системного timer или внешней выгрузки.
- Существующих тестов и примеров в репозитории нет. Основа HTTP-проверок — официальный подход FastAPI TestClient; искусственная архитектура ради тестируемости не создаётся. Отдельные модульные тесты добавляются только если важное поведение невозможно устойчиво проверить через согласованные границы.

### Приёмочные проверки API

| Область | Сценарий и ожидаемое наблюдаемое поведение |
| --- | --- |
| Доступ | Без входа нельзя читать день, сводки, историю базы, экспорт или менять данные; истёкшая и отозванная сессии также отклоняются. Прямой запрос API не обходит защиту. |
| Сессии | Два устройства входят независимо; выход одного не отключает другое; административная смена пароля отключает оба. Проверяются cookie и серверные 30 дней с управляемым временем. |
| Защита | Изменения без CSRF или с чужим Origin отклоняются, включая вход/выход. Неверные попытки входа ограничиваются и после перезапуска; комментарий с HTML/скриптом отображается как текст. |
| Ввод | Сахар отдельно, подколка отдельно, комментарий отдельно и все вместе сохраняются. Пустая запись и запись только с причиной отклоняются; 0 и пустая подколка эквивалентны. Проверяются точка/запятая, точность, отрицательные значения, `NaN`, переполнение и длина комментария. |
| Время | Запись в 23:59 и ровно 00:00 попадает в правильные московские дни при другой зоне браузера/сервера. Время создания отличается от введённого события; изменение комментария не меняет время события. Метки без смещения отклоняются. |
| Повторы и ошибки | Потеря ответа после commit и повтор операции создают ровно одну запись/версию/временную базу. Другой запрос с тем же UUID даёт конфликт. Повтор создания после удаления не восстанавливает запись. При сбое commit нет частичных изменений или квитанции успеха. |
| Конкурентные правки | Два изменения одной редакции не могут оба затереть друг друга; проигравшее получает конфликт. Одновременные операции временной базы не оставляют наложенных процентов. |
| Неизвестная база | До первого расписания запись разрешена и база `null`. Введение первого расписания не заполняет более раннее время нулями или будущими значениями. |
| Расписания | Начало с 00:00 обязательно; дубликаты, неверный порядок и время вне суток отклоняются. Проверяются последний интервал дня, точные границы, будущее начало и вставка версии между двумя историческими версиями. Ранний период не меняется. |
| Временная база | 120% от 0,50 даёт 0,60; 110% от 0,55 даёт 0,61; 0% от известной скорости даёт 0,00, от неизвестной — `null`. Процент следует за сменой интервала/версии. Проверяются полночь и одновременные границы. |
| Замещение | A действует 10:00–14:00, B начинается в 11:00 и заканчивается в 12:00: A заканчивается в 11:00, в 12:00 возвращается обычное расписание, A не возобновляется. Проверяются историческая вставка, изменение и удаление B с пересчётом соседей. |
| Завершение | Досрочное окончание и его исправление задним числом меняют только соответствующий период; окончание до начала отклоняется. После границы действует обычное расписание без запуска фонового задания. |
| Правки и отмена | Перенос записи на другой день обновляет обе сводки; удаление исключает запись, отмена возвращает. На границе 30 секунд отмена допускается только до истечения срока; конфликт редакции или временного начала не затирает другие данные. |
| Статистика | Для дня с 4,0 и 8,0: среднее 6,0, минимум 4,0, максимум 8,0, число 2. На следующий день одно 12,0: все значения 12,0; за период среднее 8,0, а не среднее дневных 9,0. День без измерений — разрыв и `null`. |
| Экспорт | Схема валидна; есть старые записи, все версии базы, настройки, удалённые записи, нули и `null`, Unicode-комментарии. Нет секретов и сессий; нет обрезания периодом/страницей. Параллельное изменение не создаёт смесь состояний разных моментов. |
| Миграции и перезапуск | После перезапуска и миграции сохраняются UUID, значения, времена, удаления и версии расписаний. Повтор миграции не создаёт пустую БД; обновление со снимка предыдущей схемы проверяется по мере появления миграций. |

### Приёмочные проверки интерфейса

1. На телефоне и компьютере: вход → открыть быстрый ввод → внести сахар с запятой → сохранить → увидеть запись и правильную базу. На iPhone отдельно проверить клавиатуру, фокус и отсутствие перекрытия кнопки сохранения.
2. Внести подколку без сахара и отдельный комментарий; получить понятную ошибку пустой записи, сохранив другие введённые поля.
3. Оборвать связь при сохранении, вернуть её и повторить: данные формы сохранены, в истории одна запись. Проверить истечение сессии во время заполнения и повтор после входа без скрытого успешного сохранения.
4. Изменить время записи, удалить и отменить удаление; проверить уведомление о конфликте со второго устройства.
5. Создать расписание и временную базу, просмотреть исторический день, завершить временную базу задним числом; интерфейс показывает именно затронутый период и подпись «по расписанию».
6. Открыть неделю, месяц и произвольный период, проверить пропуск дня и переход к исходным измерениям, доступную таблицу и управление клавиатурой.
7. Скачать полный экспорт и проверить читаемость имени/содержимого на iPhone и компьютере; увидеть состояние резервирования в настройках.
8. Вручную оценить тёмную тему, контраст, крупные кнопки и удобство после пары дней использования. Это проверка удобства, а не замена автоматическим проверкам сохранности.

### Приёмочные проверки эксплуатации

1. На реальном окружении проверить HTTPS, закрытый внутренний порт, права файлов, запуск после перезагрузки, сохранение БД между релизами, системное время и отсутствие секретов/данных в логах.
2. Создать внешнюю копию во время записи в БД; восстановить её и проверить целостность, полные данные и согласованность границ расписаний. Сверять контрольные данные снимка, а не более позднее состояние живой БД.
3. В тестовом хранилище создать восемь успешных ежедневных точек с управляемыми датами: остаются семь последних ежедневных, включая всю старую историю. Повтор за день, смена имени хоста, ручная копия и пропущенный день не ломают правило.
4. Смоделировать недоступное хранилище, неверные реквизиты, недостаток места и прерванную загрузку: старые копии остаются, новый запуск не объявляется успешным, ротация не уничтожает доступное восстановление. Статус ошибки и просрочки виден.
5. До первых реальных данных восстановить выбранную внешнюю точку в чистое окружение, пользуясь только инструкцией и сохранёнными отдельно реквизитами. Проверить вход, отзыв восстановленных сессий, все сущности, историческую базу, сводки и экспорт. Записать дату, идентификатор точки, версию приложения, результат и фактическую длительность без секретов.
6. Проверить недельное автоматическое восстановление и чтение данных репозитория, включая неуспешный результат и предупреждение. После изменений схемы повторить учение; рабочая БД остаётся нетронутой.

## Out of Scope

- Структурированный учёт еды и воды, продукты, порции и калькулятор еды; привычки, книги, прогулки и упражнения. Упоминать их в свободном комментарии разрешено.
- LLM, голосовой ввод, Telegram, Алиса, Apple Health, импорт глюкометра/помпы и любые другие интеграции ввода.
- Расчёт рекомендуемых доз, медицинские советы, подтверждение фактической подачи, растянутые/комбинированные болюсы и отдельный учёт остановок помпы.
- Другие пользователи, роли, публичная регистрация, почтовое восстановление, отчёты для врача, общий балл здоровья и игровые награды.
- Офлайн-работа, нативное iOS-приложение, push-напоминания, универсальная платформа будущих модулей, микросервисы, очереди и кэш-сервер.
- CSV, пользовательский импорт JSON, видимая история всех правок записей, автоматическое бессрочное хранение всех редакций и ежедневных резервных точек сверх семи.
- Нагрузочная платформа и высокая доступность на нескольких VPS. Измерение работы на реальном объёме и отсутствие потери данных при конкурентных запросах остаются обязательными.

## Further Notes

### Непроверенное окружение и условия запуска

VPS уже существует, но его окружение не проверено. В репозитории нет адреса подключения, описания ОС, характеристик, инфраструктурной конфигурации или выбранного внешнего хранилища. SSH-подключение, установка пакетов, создание ресурсов и замеры не выполнялись. Следующие сведения нужны для конкретизации развёртывания, но не блокируют реализацию локального дневника по этой спецификации:

| Что уточнить или проверить | Для какого решения |
| --- | --- |
| Адрес VPS, способ SSH-доступа и разрешённые административные действия; секреты передавать защищённо | Фактическая проверка и настройка окружения. |
| ОС, архитектура, обновления безопасности, поддержка Docker Engine/Compose v2 и Linux-контейнеров | Совместимость контейнерного развёртывания; Python и SQLite поставляются в образе. |
| CPU, RAM, свободное место, тип/надёжность локального диска и ожидаемое соседство с другими сервисами | Проверка пригодности SQLite, места для снимка и восстановления; характеристики не выдумываются. |
| Существующие веб-сервер, порты, firewall, запуск Docker после перезагрузки и планировщик | Запуск через Docker Compose — требование пользователя; проверить 80/443, постоянные тома и совместимость с соседними сервисами. |
| Домен, управление DNS, HTTPS-сертификаты и возможность исходящих соединений | Единый HTTPS-origin для React и API, доставка копий. |
| Провайдер/регион внешнего хранилища, доступ и допустимые дополнительные расходы | Проверка независимости от VPS, шифрования, загрузки, ротации и реальной цены. Google Drive не считается выбранным. |
| Где владелец хранит реквизиты восстановления отдельно от VPS | Возможность восстановления при полной потере сервера. |
| Реальная версия iOS/Safari и настольный браузер пользователя | Финальная проверка интерфейса на используемых устройствах. |

До запуска с реальными данными должны быть сняты вопросы доступа, HTTPS, постоянного диска, внешнего хранилища и независимого хранения ключей; восстановление должно пройти успешно. Статус `ready-for-agent` означает готовность спецификации к реализации и не утверждает готовность непроверенного VPS к эксплуатации.

### Основания решений

- Согласованные продуктовые требования, карта интервью и словарь проекта прочитаны полностью; этот документ ограничивает работу первым этапом. Новых продуктовых интервью и изменений словаря или исходных требований не требуется.
- FastAPI выбран пользователем; React + TypeScript + Vite предложены для фронтенда. Пользователь подтвердил границы проверок сообщением «подходит» после описания этого варианта.
- Официальный [Full Stack FastAPI Template](https://fastapi.tiangolo.com/project-generation/) использует React, TypeScript и Vite; весь шаблон с его дополнительными возможностями не переносится автоматически.
- [FastAPI: тестирование](https://fastapi.tiangolo.com/tutorial/testing/) — основание основной HTTP-границы. [Документация безопасности FastAPI](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/) описывает `pwdlib` и Argon2; её пример JWT не определяет выбранный здесь механизм серверных сессий.
- [SQLite Online Backup API](https://www.sqlite.org/backup.html) — согласованный снимок работающей БД. [SQLAlchemy: SQLite](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html) и [Alembic: batch migrations](https://alembic.sqlalchemy.org/en/latest/batch.html) — особенности транзакций и миграций выбранной БД.
- [restic: хранение снимков](https://restic.readthedocs.io/en/stable/060_forget.html), [проверка репозитория](https://restic.readthedocs.io/en/stable/045_working_with_repos.html) и [восстановление](https://restic.readthedocs.io/en/stable/050_restore.html) — основа резервирования. Конкретная политика семи ежедневных точек должна быть проверена тестом, а не предполагаться правильной по одному имени параметра.
