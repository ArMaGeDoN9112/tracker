# Переход к Clean Architecture

## Notes

- Запрос и открытые решения: [spec.md](spec.md).
- `diary/app.py` собирает приложение, выполняет SQL для доступа и сессий,
  задаёт middleware и преобразование ошибок в HTTP.
- `diary/entries.py` и `diary/basal.py` пока совмещают HTTP, SQL и правила
  операций. Вода перенесена в application/domain/infrastructure/interfaces;
  зависимости подключает `bootstrap.py`, старый `diary/water.py` удалён.
- `diary/backup.py` объединяет резервирование, CLI и HTTP статуса;
  использует `full_export` из `diary/export.py`.
- Уже существуют API-тесты в `tests/`; перенос должен учитывать также
  административные команды и резервирование.

## Decisions-so-far

- Q1: правила и сценарии проверяются без HTTP и реальной БД;
  обработчики и хранение можно менять независимо.
- Q2: весь бэкенд, включая авторизацию, экспорт, backup и admin CLI;
  фронтенд вне объёма рефакторинга.
- Q3: сохранить API, данные, экспорт, команды и поведение.
- Q4: поэтапный переход с работоспособным приложением после каждого этапа.
- Q5: Pydantic допустим в ядре; HTTP, SQL и файловые операции остаются снаружи.
- Q6: четыре пакета domain/application/infrastructure/interfaces.
- Q7: каждый сценарий — отдельный класс; явные зависимости, без DI-фреймворка.
- Q8: Unit of Work и интерфейсы хранения под нужды сценариев;
  одна атомарная транзакция для данных и квитанции, единый снимок чтения.
- Q9: DTO переиспользуются при совпадении смысла и полей; принадлежат application.
- Q10: типизированные исключения без HTTP-статусов; адаптеры сохраняют API-ответы.
- Q11: конструктор с зависимостями, execute с DTO; явные часы и генераторы ID.
- Q12: общие типы/расчёты → вода → дневник/база → продукты/питание →
  графики/сводки → экспорт/backup → доступ/admin.
- Q13: unit-проверки ядра, интеграционные SQLite, API-регрессия,
  автоматическое правило импортов и Docker Compose.

## Риски, подтверждённые обследованием

- Запись и квитанция операции должны использовать одно соединение и одну
  транзакцию `BEGIN IMMEDIATE`; хеш прежних запросов должен совпадать после переноса.
- Составные чтения и экспорт должны сохранять единый снимок SQLite.
- `full_export` используется проверкой резервной копии; перенос затрагивает CLI.
- Тесты подменяют часы по путям старых модулей; фикстуры тоже входят в перенос.
- Неудачный вход сохраняет счётчик до отказа: исключение не должно откатить
  эту фиксацию. Backup/restic не образуют общую транзакцию с SQLite.
