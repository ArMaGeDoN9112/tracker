# Переход к Clean Architecture

Status: resolved

## Запрос

Спланировать переход проекта, как минимум бэкенда, к Clean Architecture.
Реализация рефакторинга в текущий запрос не входит.

## Исходные ограничения

- Сохранять правила из `docs/agents/code-feedback.md`: SQLAlchemy Core,
  конкретные Pydantic DTO, enum действий и совместимость сохранённых значений.
- Использовать единый предметный контекст и термины из `GLOSSARY.md`.
- Запуск и проверки проекта выполнять через Docker Compose.

## Согласовано

1. Цель: тестировать бизнес-правила и сценарии без HTTP и реальной БД;
   менять обработчики и хранение независимо.
2. Объём: весь бэкенд — дневник, база, питание, вода, авторизация,
   экспорт, резервирование и административные команды. Фронтенд вне рефакторинга.
3. Сохранить API, существующие данные SQLite, формат экспорта, команды запуска
   и поведение, включая повтор прежних UUID, конфликты версий и отмену удаления.
4. Переходить небольшими завершёнными этапами; приложение работает после каждого.
5. В domain и application разрешён Pydantic; запрещены зависимости от FastAPI,
   SQLAlchemy, SQL и файловых операций.
6. Пакеты `diary/domain`, `diary/application`, `diary/infrastructure`,
   `diary/interfaces`; внутри группировка по функциям проекта.
   Внутренние слои не импортируют внешние. Сборка связывает реализации с интерфейсами.
7. Каждый сценарий — обязательный отдельный класс, включая простые операции.
   Зависимости передаются явно; DI-фреймворк не требуется.
8. Application определяет границу операции через интерфейс Unit of Work;
   инфраструктура обеспечивает соединение, блокировку, commit/rollback.
   Интерфейсы хранения соответствуют нуждам сценариев; запись и квитанция UUID
   сохраняются атомарно; составные чтения используют единый снимок.

9. HTTP и сценарий переиспользуют DTO, когда смысл и поля совпадают.
   DTO сценария принадлежит application. Разные представления требуют разных DTO.
10. Ожидаемые отказы — типизированные исключения без HTTP-статусов.
    HTTP и CLI преобразуют их в прежние ответы. Адаптеры переводят ошибки
    инфраструктуры в ошибки приложения с сохранением причины.
11. Зависимости сценария передаются в конструктор, входной DTO — в `execute`,
    результат типизирован. Часы и генераторы идентификаторов передаются явно;
    реальные реализации подключаются при сборке HTTP или CLI.
12. Порядок: общие типы и расчёты → вода → дневник и база → продукты и питание
    → графики и сводки → экспорт и резервирование → авторизация и admin CLI.
13. Приёмка: проверки правил и сценариев без БД, интеграционные проверки SQLite,
    сохранение API-тестов, автоматическая проверка направления импортов.
    Все исполняемые проверки — через Docker Compose; в финале весь бэкенд
    и затронутые сквозные сценарии.

## Целевая структура и зависимости

```text
diary/
  domain/
    ...                # предметные модели, расчёты, инварианты
  application/
    ...                # классы сценариев, DTO, ошибки и интерфейсы зависимостей
  infrastructure/
    ...                # SQLAlchemy Core, SQLite, restic, файлы, криптография
  interfaces/
    http/              # обработчики, middleware, HTTP DTO и отображение ошибок
    cli/               # argparse, скрытый ввод, вывод и коды завершения
  bootstrap.py         # явная сборка зависимостей для точек входа
  app.py               # совместимый create_app / from_env
  admin.py             # совместимый python -m diary.admin
  backup.py            # совместимый python -m diary.backup
```

Внутри слоёв группировать файлы по существующей функциональности: вода,
дневник, база, продукты, приёмы пищи, доступ, экспорт и резервирование.
Domain не импортирует application, infrastructure или interfaces.
Application импортирует domain и собственные интерфейсы зависимостей.
Infrastructure реализует эти интерфейсы; interfaces вызывает application.
Только сборка связывает внешние реализации с внутренними интерфейсами.
Обратные импорты через старые модули, включая локальные импорты внутри функций,
не являются допустимым обходом правила.

Каждая самостоятельная операция чтения или изменения — класс сценария.
Примеры: `CreateWater`, `EditWater`, `DeleteWater`, `RestoreWater`, `GetWater`.
Публичный метод — `execute`; зависимости живут в конструкторе.
Не нужен общий базовый класс сценариев или обязательный отдельный файл на класс.
Вспомогательные расчёты остаются функциями, если им не требуется состояние.
Общие шаги квитанций и изменения записей переиспользуются между классами;
не копировать транзакционный алгоритм для каждого действия.

DTO и доменные модели не содержат FastAPI Response/Request, SQLAlchemy Row,
Connection или Engine. SQL-строки и преобразование mappings остаются в адаптере.
API-модель можно переиспользовать только после переноса её во внутренний слой
и проверки отсутствия транспортных зависимостей.
HTTP-форматирование дат, cookie, заголовки и статусы принадлежат HTTP-адаптеру;
правила времени события, точности и округления принадлежат ядру.
Не менять прежний алгоритм нормализации и хеширования команд ради нового DTO.

## Транзакции и внешние эффекты

- Для одного вызова сценария создаётся отдельный Unit of Work; соединение
  не разделяется между запросами. Репозитории не открывают свои соединения
  и не делают самостоятельный commit.
- Сценарий задаёт момент фиксации; SQLite-адаптер реализует его. Для записи
  сохранить `BEGIN IMMEDIATE`, проверку UUID, ревизии, изменение и квитанцию
  в одной транзакции. Ошибка до фиксации откатывает всю операцию.
- Повтор существующего UUID проверяет тот же action и прежний request_hash;
  повтор не создаёт новую запись и не продлевает срок отмены.
- Составные чтения, день, сводки и экспорт используют один снимок.
  Допустимы специализированные порты чтения: не собирать их через множество
  раздельных транзакций и не делать универсальный CRUD-репозиторий.
- Отказ не всегда означает rollback: неверный пароль должен сначала сохранить
  счётчик неудачных входов и только затем вернуть ожидаемый отказ.
  Аналогично сохранить текущую фиксацию очистки счётчиков при 429.
  Смена пароля и отзыв сессий остаются одной атомарной операцией.
- Файлы и restic не входят в SQLite-транзакцию. Сценарии backup/restore управляют
  шагами через порты; сохранить существующие блокировку, проверки, статусы,
  обработку частичных сбоев и порядок ротации. Не объявлять их общей атомарной UoW.
- Время и UUID подставляются в тестах. Токены сессий требуют отдельного
  криптографически стойкого генератора: UUID не заменяет `secrets.token_urlsafe`.
- Инфраструктурная ошибка сохраняет исходную причину для диагностики;
  HTTP/CLI не раскрывают SQL-параметры, пароли, токены и внутренние сообщения.

## Этапы и критерии приёмки

Каждый этап — законченный перенос с рабочими HTTP/CLI точками входа.
Если этап велик, делить на PR по связанным сценариям, не оставляя приложение сломанным.

| № | Результат | Основные затронутые места | Условие завершения |
|---|---|---|---|
| 01 | Зафиксирована исходная совместимость | tests, Docker checks, контракты API/экспорта | Исходные проверки выполнены; пробелы по критическим инвариантам закрыты до переноса |
| 02 | Подготовлены внутренние типы и расчёты | dto, entries, basal, products, meals, security | Чистые расчёты и DTO не тянут HTTP/SQL; старые вызовы работают; добавлена проверка импортов |
| 03 | Вода целиком проходит через новые слои | water, общие квитанции/UoW, дневное чтение, tests | Классы чтения/изменения/настроек; replay, rollback, версии и граница отмены проверены |
| 04 | Перенесены дневник и база | entries, basal, их вызовы из чтений/экспорта | Версии расписаний, проценты, пересечения, неизвестная база и историческое время сохранены |
| 05 | Перенесены продукты и приёмы пищи | products, meals, снимки строк приёма пищи | Точность, неизвестные нутриенты, порции, история состава и повтор приёма пищи сохранены |
| 06 | Перенесены графики и сводки | glucose, чтение дня, nutrition, water | Единый снимок чтений, прежние периоды, суммы, средние и порядок результатов |
| 07 | Перенесены экспорт и резервирование | export, backup, status, CLI, docs/export, Docker | Экспорт прежнего формата; снимок во время записи, restore, отзыв сессий, ошибки restic и ротация проверены |
| 08 | Перенесены доступ и admin CLI | app, security, admin, middleware, db/migrate | CSRF/cookie/Host/Origin, лимиты, сессии, пароли, миграции и команды работают как прежде |
| 09 | Завершён перенос и удалены временные мосты | сборка, старые модули, tests, scripts, Docker, документация | Полный набор проверок зелёный, запрещённых импортов нет, старые entrypoints сохранены |

Детали и зависимости этапов: [задачи](issues/01-baseline.md).
Временные совместимые импорты допустимы только для ещё не перенесённых модулей
и должны быть перечислены в задаче этапа. Перенесённое ядро не импортирует эти мосты.
Общие компоненты извлекать по нуждам текущего этапа; не строить заранее
инфраструктуру для всех будущих сценариев.

## Стратегия проверок

- Использовать существующие tests/test_*.py как регрессионную защиту;
  менять фикстуры и пути подмены часов вместе с переносом, сохраняя смысл проверок.
- Проверки domain — без HTTP/БД; application — с подставными портами,
  часами и генератором ID. Проверять исходы и эффекты, а не порядок внутренних вызовов.
- Интеграционные проверки — временная файловая SQLite с реальными миграциями:
  совместное соединение, откат, конкуренция, снимки чтений и прежние квитанции.
- До изменения модели команд сохранить синтетические запросы/квитанции прежнего
  формата и проверить их replay новым кодом; не генерировать все эталоны новым алгоритмом.
- Автоматическая проверка импортов должна охватывать локальные и относительные
  импорты, запрещать ссылки ядра на старые инфраструктурные модули и контролировать
  зависимости на уровне модулей, а не только названий четырёх папок.
- На каждом этапе выполнять профильные тесты и mypy; полный набор backend —
  в контрольных точках и обязательно в финале. Проверки правил импортов запускаются
  с обычным pytest. Не добавлять зависимость ради простой проверки импортов.
- Финал: backend, mypy, сборка frontend и существующие e2e. Отдельно проверить
  старые команды запуска/CLI и восстановление резервной копии на синтетических данных.

Команды из текущего README:

```sh
docker compose run --build --rm checks
docker compose run --rm checks mypy
docker compose build front
docker compose run --build --rm e2e
```

Для профильной проверки: `docker compose run --build --rm checks pytest -q tests/test_water.py`.
Контейнеры проверок используют временные данные; рабочую БД не подключать.

## Область изменений и совместимость

- Код: весь `diary`, включая таблицы, создание engine и служебные миграции;
  SQLAlchemy Core остаётся инфраструктурным инструментом.
- Вызовы: HTTP-регистрация, взаимные вызовы функциональных модулей,
  экспорт, проверка backup, CLI и сборка приложения.
- Проверки: существующие API/SQLite/backup-тесты, фикстуры, monkeypatch,
  scripts и frontend e2e, если они ссылаются на перемещённые модули.
- Упаковка: `Dockerfile`, `compose.yaml`, содержимое backup bundle,
  публичные команды `diary.app:from_env`, `python -m diary.admin`,
  `python -m diary.backup`. Сохранять их через тонкие точки входа.
- Документация: ADR, README и эксплуатационные инструкции актуализируются
  при затрагивающих их изменениях. GLOSSARY остаётся предметным словарём;
  термины слоёв и классов туда не добавляются.
- Изменения схемы БД и формата экспорта для этого рефакторинга не планируются.
  Новые функции, PostgreSQL, DI-контейнер, CQRS/event bus и универсальные
  базовые репозитории в объём не входят.
- Рабочие данные не преобразовывать и не удалять. При развёртывании проверить
  резервную копию; этап должен позволять возврат прежнего кода на той же схеме.

## Итоговая приёмка

1. Каждый HTTP/CLI сценарий представлен классом application; адаптеры
   не содержат SQL или предметных правил.
2. Domain/application не зависят от HTTP, SQLAlchemy, файлов, restic
   или старых модулей, содержащих эти зависимости.
3. Инфраструктурные адаптеры реализуют нужные сценариям интерфейсы;
   соединения и фиксация не спрятаны в отдельных репозиториях.
4. Поведение API, данные, экспорт, backup/restore и команды совместимы.
5. Все указанные проверки выполнены; временные мосты удалены, кроме
   намеренно сохраняемых публичных точек входа.
