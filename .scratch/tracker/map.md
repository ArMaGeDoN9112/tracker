# Проектирование личного трекера

## Notes

- Продуктовое интервью завершено: пользователь согласовал спецификацию (Q86) и последние 7 ежедневных копий (Q87). Реализация не начата; техническая подготовка первого этапа впереди.
- Цель пользователя: видеть данные о разных сторонах жизни в одном месте, без отдельных платных приложений.
- Сейчас дневник не ведётся. Раньше использовались бумажные дневники; их сложно анализировать.
- Ввод возможен в любое время и в любом месте с iPhone и компьютера.
- Помпа: Accu-Chek Combo (пользователь написал «accu check combo»).
- Глюкометр: OneTouch Select Plus Flex.
- Пользователь хочет просматривать определённый день и график среднего из внесённых измерений за каждый день с отображением дневных минимумов и максимумов, за неделю, месяц или произвольный период.
- Для первичной оценки удобства пользователю достаточно пары дней использования.

## Decisions-so-far

- Только один пользователь; доступ других людей и отчёты для них пока не нужны.
- Первый этап — дневник диабета с ручным вводом собственных данных.
- Расчёт доз инсулина не нужен.
- Подколка включает введение на еду и коррекцию; база означает базальную скорость помпы. Термины записаны в [словаре](../../GLOSSARY.md).
- Пустая подколка и подколка 0 равнозначны по решению пользователя. Растянутые и комбинированные болюсы не используются; первая версия их не включает.
- Единицы: сахар — ммоль/л, подколка — единицы инсулина, база — единицы в час. Сахар и подколка — один знак после запятой; любая база — два знака после запятой (уточнение Q42).
- Используется одно обычное суточное расписание базы. Интервалы задаются временем начала и скоростью с 00:00; последний действует до полуночи. Новое расписание действует с выбранных даты и времени, прежняя база в истории сохраняется.
- Временная база задаётся началом, продолжительностью и процентом от обычного расписания (например, 120%). Можно завершить раньше, включая исправление окончания задним числом; затем снова действует обычное расписание.
- До интеграции с помпой база показывается «по расписанию» с учётом внесённых временных изменений. Отдельный учёт остановок подачи пока не нужен; в будущем пользователь рассматривает связь с действиями, например походом в бассейн.
- Новая временная база прекращает предыдущую с момента начала, проценты не накладываются.
- Дата и время по умолчанию текущие, допускается ввод задним числом. Время события и время создания записи различаются. Для всего дневника согласован московский часовой пояс.
- Записи можно редактировать и удалять с отменой удаления; видимая история изменений не нужна.
- Основное действие — быстрый ввод: фокус на сахаре, текущее время, необязательная подколка, база по расписанию. Сохранять только подколку можно; запись без сахара, ненулевой подколки и комментария не сохраняется.
- Причина подколки (еда, коррекция, еда и коррекция) необязательна и не угадывается из комментария.
- В первой версии сведения о еде сохраняются текстовым комментарием. На этапе еды обязателен пересчёт заданных пользователем пищевой ценности и количества; распознавание продукта/порции по тексту или фото — отдельная будущая возможность.
- Согласован порядок этапов: (1) дневник диабета и графики, (2) продукты, дневник еды, расчёт БЖУ/калорий и вода, (3) привычки, чтение и упражнения, (4) голосовой ввод с подтверждением. Возможности импорта ещё предстоит проверить.
- График: линия дневного среднего, диапазон минимум–максимум, число измерений, открытие исходных измерений по нажатию на день. Дни без измерений остаются пропусками; при одном измерении среднее, минимум и максимум совпадают. Среднее за период считается по всем измерениям, а не по средним дней.
- Голосовой ввод и LLM отложены до определения типов данных и предметных областей. В перспективе распознанные действия должны показываться пользователю для подтверждения. Правила для недостающих количеств пока не уточнены.
- Сервис планируется на VPS с доступом через интернет с разных устройств. Работа без интернета не требуется.
- Google Drive был примером, а не выбранным местом резервного копирования. Выбор внешней LLM отложен.
- Пользователь хочет попробовать несколько вариантов отображения привычек, прежде чем выбрать подходящий. Конкретные варианты пока не согласованы.
- «Качество жизни» означает просмотр фактических данных без общего автоматического балла: выполненные и невыполненные привычки, средний сахар, сводки по еде и физической активности.
- Один личный аккаунт с паролем и сохранением входа на устройствах.
- Ежедневная автоматическая резервная копия отдельно от VPS и ручная выгрузка всех данных. Потеря записей за последний день при аварии допустима.
- VPS уже есть.
- Для продуктов БЖУ и калории задаются на 100 г либо 100 мл; автоматического перевода граммов в миллилитры нет. Все известные значения пересчитываются на съеденное количество, включая часть упаковки.
- Именованные порции задаются пользователем с количеством граммов или миллилитров (ломтик, упаковка, стакан и т.п.).
- Приём пищи объединяет несколько продуктов общим временем и итоговыми БЖУ/калориями; название категории приёма пищи необязательно.
- Разовая еда не требует добавления в каталог; значения можно вводить за съеденную порцию без веса. Можно позже сохранить как постоянный продукт; правила перевода в карточку на 100 г/мл ещё не уточнены.
- Еду можно сохранять с неполными сведениями. Неизвестные значения не равны нулю; сводки обозначают неполноту.
- Изменение карточки продукта не меняет прошлые приёмы пищи. Конкретную старую запись можно исправить отдельно.
- Можно повторить прошлый приём пищи с текущими датой/временем, проверить состав и изменить количества перед сохранением.
- Отдельный редактор рецептов пока не нужен: пользователь готов разбивать составное блюдо на простые продукты и учитывать их отдельно.
- Калории берутся с этикетки на 100 г/мл и вместе с БЖУ пропорционально пересчитываются на съеденное количество (Q52).
- Каталог продуктов сначала наполняется вручную; поиск по своему каталогу и создание продукта при записи еды. Сторонние базы, штрихкоды и распознавание этикеток отложены.
- Сводка еды: БЖУ/калории за день, история приёмов пищи и средние за период без целевых норм и оценок. Для средних показывается число дней с записями; дни без записей не считаются нулевым потреблением.
- Привычки добавляются через удобный редактор без изменения кода. Первые примеры: чтение с количеством страниц, зарядка, прогулка. Вода вынесена из привычек в отдельный учёт в разделе питания (Q65).
- Базовые типы привычек: отметка и количество; несколько количественных записей складываются за день. Связи с книгами и упражнениями описаны ниже.
- Для чтения нет цели по страницам: важны факт чтения и фактическое количество страниц. Ранее предложенное правило достижения цели к чтению не применяется.
- Состояния привычки: выполнено, явно не выполнено, нет записи. Обязательного расписания нет. Сводка за период: количества дней каждого состояния и календарь; дни до создания, после архивирования и во время паузы исключаются.
- День привычек — календарный по Москве; доступен выбор сегодня/вчера/другая дата.
- Изменение условий привычки не меняет прошлые результаты (Q61); какие условия нужны помимо чтения без цели — ещё уточняется.
- Поддерживаются пауза и архив привычки с сохранением истории; дни паузы исключаются из сводки состояний.
- Напоминания пока не нужны.
- Общий редактор привычек: название, тип (отметка/количество), единица измерения для количества, необязательное описание. Цели необязательны; у чтения цели нет.
- Чтение: выбор книги и ввод количества страниц; несколько книг и записей за день, в привычке общий итог, в подробностях — книги. Обязательной закладки по номеру страницы нет.
- Карточка книги: название, автор, необязательное число страниц, статус хочу прочитать/читаю/прочитана/отложена. Можно добавить ранее прочитанную книгу без истории чтения. Обложки и внешние каталоги пока не нужны.
- Вода: настраиваемые кнопки объёмов и произвольный ввод в мл; отдельная запись со временем на каждое добавление, дневная сумма, отмена ошибочного добавления. Пока без суточной цели. Учитывается только явно добавленная вода; напитки из еды автоматически не прибавляются.
- Прогулка — простая отметка, без обязательной продолжительности, GPS и шагов.
- Упражнение: название, способ учёта (повторения/время/отметка). Комплекс — именованный упорядоченный набор упражнений с возможными плановыми количествами. Вес, подходы и отдых пока не требуются.
- Обычный сценарий зарядки — одна кнопка «Выполнил зарядку». Отдельное отмечание упражнений и частичное выполнение пока не подтверждены и не включены в обязательный объём.
- Сводка активности: число прогулок, число выполненных комплексов и общая продолжительность там, где она записана; без расчёта потраченных калорий.
- Дневник доступен до настройки базы: значение обозначается как неизвестное, а не ноль; расписание применяется только в пределах своего срока действия.
- Записи чтения автоматически означают выполнение. Внесение страниц заменяет явное невыполнение; при наличии записей нельзя поставить невыполнение без их исправления. Удаление всех записей возвращает состояние «нет записи».
- Выполнение комплекса создаёт одну связанную запись активности и выполнения привычки. Исправление/удаление отражается в обоих представлениях; состав комплекса сохраняется на момент выполнения.
- Продолжительность комплекса необязательна и не запрашивается при быстром выполнении; в сумму минут входят только явно внесённые значения.
- Пароль восстанавливается административной командой на VPS с документированной инструкцией; почтового восстановления пока нет.
- Ручная выгрузка — полный архив всех данных в документированном JSON. CSV пока не требуется.
- Интерфейс спокойный, с крупными полями/кнопками, без игровых наград и общего балла здоровья. Тёмная тема приоритетна; телефон — прежде всего быстрый ввод, компьютер — также история и графики.
- Вся накопленная история данных хранится бессрочно. Для восстановления хранятся последние 7 ежедневных полных резервных копий отдельно от VPS (Q87); каждая включает всю накопленную историю. Ошибка, обнаруженная после смены всех копий, может оказаться невосстановимой.
- Сводная спецификация: [spec.md](spec.md); продуктовые требования согласованы. Статус needs-triage обозначает необходимость технической подготовки первого этапа, а не ожидание ответов на интервью.

- Выбран и перенесён интерфейс C: компоновки всех разделов, сохранение операций,
  рабочая оболочка во всю ширину окна. Текущее поведение — в
  [docs/diabetes-diary.md](../../docs/diabetes-diary.md). Спецификация завершённого
  редизайна сохранена в коммите `371c78bad2dc5c7fcaa1c2b7bc83f0488613272c`
  ветки `codex/ui-redesign-prototypes-20261029` (`.scratch/ui-redesign/spec.md`);
  проверочные скриншоты и временные галереи удалены по запросу пользователя.

## Fog

- Округление вычисленной базы до двух знаков после применения процента.
- Поведение при повторной отправке и ошибках сохранения.
- Срок отмены удаления и расположение ручной выгрузки.
- Сохранение разовой еды в каталог без известного веса — уточнить при детализации этапа питания.
- Место хранения резервных копий — выбрать при технической подготовке.
- Возможности импорта устройств и Apple Health не исследованы; для первой версии импорт не обещан.
- Технологии первого этапа: FastAPI, React + TypeScript + Vite, SQLite; по требованию пользователя весь запуск и проверки — через Docker Compose. Окружение существующего VPS, внешнее хранилище и дополнительные расходы ещё требуют проверки; команды запуска — в [README](../../README.md).
